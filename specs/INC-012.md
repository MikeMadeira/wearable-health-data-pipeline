## 1. Profile of the real input (observed vs assumed)

Observed, profiled read-only on `data/health_summaries/device_metadata.csv` (not modified, not committed):

- 50 rows, 50 distinct `device_id`, 50 distinct `participant_id`: no duplicate device rows.
- All 50 `calibration_date` values match `^\d{4}-\d{2}-\d{2}$` (uniform ISO 8601 date, no time part, no blanks) and are calendar-valid.
- Range 2025-12-04 .. 2026-01-07; every date precedes the default `study_start` 2026-01-08 (`pipeline.DEFAULT_STUDY_START`).
- Against 2026-01-08: 10 dates are strictly more than 30 days before (calibrated on or before 2025-12-08), exactly 1 date is exactly 30 days before (2025-12-09, not stale), 0 are on or after `study_start`, 0 are blank or unparseable.

Expected on real data (human to confirm after implementation): `DEVICE_CALIBRATION_STALE` failed = 10, `DEVICE_CALIBRATION_INVALID` failed = 0, both with `checked` = 50.

Assumed (not provable from the data): the format stays ISO `YYYY-MM-DD`; other formats seen in future exports are reported as invalid, never guessed (for example `08/12/2025` is ambiguous). The 30-day threshold and the "strictly more than" comparison come from the intent. Observed zero dates on or after `study_start`, so that branch rests on the intent and on synthetic fixtures.

## 2. Data contract

### Inputs

`health_summaries/device_metadata.csv` (grain: one row per device; key `participant_id`, cross-check `device_id`, as in INC-011) and `participants/participants.csv` (unchanged). `calibration_date` is an **optional** column: when the column is absent it reads as blank for every row (so every participant is `DEVICE_CALIBRATION_INVALID`), exactly like the optional `firmware_version` of INC-011. No new input file, and no new required column, so no new run failure.

### Date semantics

- Calibration dates are calendar dates without time zone; no conversion and no local-date logic.
- Accepted format (decision P4): after stripping surrounding whitespace, the text must match `[0-9]{4}-[0-9]{2}-[0-9]{2}` (ASCII digits) and be a valid proleptic Gregorian date (`date(y, m, d)` succeeds; year 0000 and `2025-02-30` are invalid). Everything else is unparseable: blank or whitespace-only, `None`, `2025/12/24`, `24-12-2025`, `2025-1-4`, `20251224`, `2025-12-24T10:00:00`, `2025-12-24 10:00`, `2025-12-24Z`, ISO week dates, non-ASCII digits. `datetime.date.fromisoformat` is not used directly because Python 3.11+ also accepts `20251224` and week dates.
- Reference date: the `study_start` of the run (the argument given to `run_pipeline` / `run_incremental`, default 2026-01-08). `days_before = (study_start - calibration_date).days`.
- Stale: `days_before > CALIBRATION_STALE_DAYS` (constant 30, no CLI flag, defined in `devices.py`). 29 and 30 days are not stale, 31 is. A date on or after `study_start` (`days_before <= 0`) is valid and not flagged. The window length `study_days` plays no role.

### `silver_device_metadata` (amended)

Grain and the first eight columns are unchanged from INC-011 (including `quality_flags`, which stays about firmware only). Two columns are appended, so silver has 10 columns:

| Column | Type | Meaning |
|---|---|---|
| `calibration_date_raw` | VARCHAR | raw cell, untrimmed; `''` if blank or the column is absent |
| `calibration_date` | DATE | the parsed date, NULL when blank or unparseable |

### `gold_participant_devices` (amended; supersedes the 3-column decision of INC-011 / ADR-007)

Grain and key unchanged: one row per distinct `participant_id` of `participants.csv`, key `participant_id`. Columns, exactly, in order: `participant_id VARCHAR`, `device_id VARCHAR`, `firmware_version VARCHAR`, `calibration_date DATE`. Rows sorted by `participant_id` in the layer; row order in the table is not significant.

- `calibration_date`: the parsed date of the **chosen metadata row** (same row-selection rule as `firmware_version`: first row of the participant with matching `device_id`, else the participant's first row, else none). NULL when there is no row, the cell is blank, or it is unparseable. The raw text stays in silver and in `quality_rejects.raw_values`.
- A stale date is shown as is (the finding is a flag, the value is not defaulted or hidden). The shown value does not depend on `study_start`; only the findings do.
- Existing tables (`gold_clinical_daily`, weekly, cohort, silver) keep their keys, columns and semantics; `run_id` is unchanged.

## 3. Quality rules

Two rules, source `device_metadata`, handling `flag`, severity `medium`, added to `devices.DEVICE_RULES` (merged into `pipeline.RULES` by the existing line). Both are evaluated per participant on the chosen metadata row; `checked_count` = number of distinct `participant_id` in `participants.csv` (the gold row count); `failed_count` = participants failing the rule. A participant fails at most one of the two (invalid dates are not evaluated for staleness).

| rule_id | Fails when | Reason text (exact) |
|---|---|---|
| `DEVICE_CALIBRATION_STALE` | parsed date exists and `days_before > 30` | `calibration_date is more than 30 days before study_start` |
| `DEVICE_CALIBRATION_INVALID` | no chosen metadata row, or the cell is blank, absent, or unparseable per section 2 | `calibration_date is blank or not an ISO 8601 date (YYYY-MM-DD)` |

- A participant with no metadata row has a NULL date and counts as invalid. This follows P7 of INC-011 (such a participant already counts as `DEVICE_ID_MISMATCH` and `FIRMWARE_UNRECOVERABLE`); the finding is a second view of the same defect and nothing is excluded.
- **No run failure** (decision P2): both rules only flag, per ADR-005. The participant stays in `gold_participant_devices` with all other columns intact. A missing `device_metadata.csv` or missing `participant_id` / `device_id` column still fails the run (unchanged).
- **Rejects**: one `quality_rejects` row per failing participant per rule, `source = device_metadata`, `row_ref = "<relative path>:<1-based data row>"`, `raw_values = json.dumps(raw CSV row, ensure_ascii=False)` (raw calibration text preserved, including padding). Evidence row: the chosen `device_metadata.csv` row; when the participant has no metadata row, the participant's first `participants.csv` row.
- **Report**: `quality/report.md` lists both rules in the existing table. Total rules 46 -> 48. Rules sort by id, so the two new rows come first (`DEVICE_CALIBRATION_*` < `DEVICE_ID_*`).

## 4. Run behaviour

- **Derivation** stays in the pure builder (decision P5): `build_device_layer(participants, metadata, study_start)` returns the same `DeviceLayer` with the extended silver and gold tuples, counts and rejects. `study_start` is a plain `datetime.date`; `devices.py` has no default and never reads the clock or `pipeline.py` (no circular import). Helpers: `parse_calibration_date(raw)` and `classify_calibration(raw, study_start)` (returns a rule id or `None`).
- **Full run** (`_run_full`, also the incremental fallback): `pipeline._run_full` passes its `study_start` argument to the builder; `_persist` replaces both device tables in the same transaction as today; `DEVICE_DDL` and `TABLE_DDL[silver]` follow the extended column constants.
- **Incremental** (decision P3): the device tables stay `_replace` outputs of a full rebuild. A change to `device_metadata.csv` is already a shared-source change (`shared_input_changed`, full rebuild). A changed `study_start` (or `study_days`) already compares unequal with `run_window` and gives the existing `window_changed` full rebuild; this is how a changed window reaches the rule, and no new tracking state is added. An unchanged rerun is `noop` and touches nothing. `_expected_schema` derives from the column constants, so an output with the old 3-column gold or old silver table is rebuilt with `old_schema`. Quality results of the device rules are carried over only on event-only incremental runs, which cannot change them.
- **Idempotent**: identical inputs and `study_start` give identical tables, the same `run_id` and no duplicate rows; a full run in the same directory with a different `study_start` replaces the findings in place and equals a fresh full run (the `run_id` is by design input-based and does not include `study_start`, as before).
- **compare** needs no code change (decision P6): it already compares every base table, so the gold and silver calibration columns are covered; tests prove a changed `calibration_date` (gold) and `calibration_date_raw` (silver) are detected.
- No change to CLI commands or flags, `pyproject.toml`, `uv.lock`, or `data/`.

## 10. Planning decisions (need ratification)

- P1 Storage: `calibration_date DATE` is a 4th column of `gold_participant_devices` (so analysts see it next to `device_id` and firmware, in the table they already query), plus `calibration_date_raw` and `calibration_date` in silver. Supersedes the 3-column decision (ADR-007). Justification: a silver-only date would force analysts to join a table the intent says they should not need; the cost is amended tests, done explicitly. Derivation: parse once in the pure builder, from the chosen metadata row.
- P2 Findings only flag, never fail the run and never remove the participant (ADR-005). A stale calibration is a trust signal, not a malformed input; excluding devices would silently shrink the cohort.
- P3 Incremental tracking: no new state. `device_metadata.csv` is already a shared source and `run_window` already holds `study_start`, so both change paths give a full rebuild that equals a fresh full run. Tests pin the reasons `shared_input_changed` and `window_changed`.
- P4 Accepted format: strict ISO `YYYY-MM-DD` with ASCII digits, surrounding whitespace stripped, calendar-valid; everything else is invalid and never guessed. Matches the observed uniform format; ambiguous formats (`08/12/2025`) must not be reinterpreted.
- P5 `study_start` reaches the rule as an explicit `date` argument of `build_device_layer`, passed by `_run_full` (also used by the incremental fallback). No module constant, no clock, no CLI flag for the 30 days. The parameter is optional only in the planning stub (so the red baseline is not 469 `TypeError`s) and becomes required.
- P6 `compare` is unchanged: it is generic over base tables; tests prove the new columns are compared. `run_id` and CLI are untouched.
- P7 A participant with no metadata row (NULL date) counts as `DEVICE_CALIBRATION_INVALID`, consistent with INC-011 P7. Both rules use `checked_count` = participants and severity `medium`; stale and invalid are mutually exclusive per participant.
- P8 Fixtures: layer fixtures reuse `prow`/`mrow` of `tests/test_devices.py` with a `calibration_date` override; the pipeline fixtures use `devices_data` with `START` = 2026-01-08 = the default, plus `LATER_START` = 2026-02-01 for the non-default case. The existing `mrow` date 2025-12-24 is 15 days before `START`, so it triggers nothing and the existing device tests only change by the new column.
- P9 Rule count 46 -> 48 with the amended assertions listed in section 6.
- P10 The runner artifact id is `INC-012`, so the report is `reports/INC-012/planner.md`.
