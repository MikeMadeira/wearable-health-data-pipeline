# INC-006: Incremental Mode and Output Compare

Status: Draft
Source intent: `intents/INC-006-incremental-mode-and-compare.md`
Upstream decision: `reports/INC-001/profiling-findings.md` Section 7, item 9 (G4: incremental
processing by affected participant-day, idempotent MERGE on `participant_id`, `local_date`,
changed inputs found by file manifest and checksum).
Amends: `specs/INC-002.md` (CLI line only: the `--mode` flag and `compare` subcommand are
added). Everything not named here is unchanged: `run_pipeline`, `RunResult`, `PipelineError`,
all existing tables' columns and values, `gold_clinical_daily` key and MERGE behavior, the
`run_id` derivation, the default (full) behavior and the report format.

## 1. Public contract

| Name | Module | Signature / shape |
|------|--------|-------------------|
| `run_incremental` | `incremental` | `run_incremental(data_dir: Path, output_dir: Path, *, study_start: date = date(2026, 1, 8), study_days: int = 28) -> IncrementalResult` |
| `IncrementalResult` | `incremental` | frozen dataclass: `run_id: str`, `database_path: Path`, `report_path: Path`, `outcome: str`, `fallback_reason: str \| None`, `new_paths: tuple[str, ...]`, `changed_paths: tuple[str, ...]`, `removed_paths: tuple[str, ...]`, `affected_gold_rows: int` |
| `ManifestDiff`, `diff_manifests` | `incremental` | `diff_manifests(previous: Mapping[str, str], current: Mapping[str, str]) -> ManifestDiff` (frozen dataclass with sorted tuples `new`, `changed`, `removed`, `unchanged`); pure |
| `changed_days` | `incremental` | `changed_days(previous: Sequence[tuple], new: Sequence[tuple], date_index: int = 1) -> frozenset[date]`; pure |
| `read_event_file` | `incremental` | `read_event_file(path: Path, relative: str, kind: str) -> list[Any]`; the only parser of event JSON in incremental mode |
| `DerivedTable`, `DERIVED_TABLES` | `incremental` | extension point (section 9) |
| `compare_outputs`, `format_comparison` | `compare` | section 8 |
| `CompareResult`, `TableDiff` | `compare` | frozen dataclasses, section 8 |

Outcome constants: `OUTCOME_INCREMENTAL = "incremental"`, `OUTCOME_NOOP = "noop"`,
`OUTCOME_FULL = "full"`. `run_pipeline` keeps its signature; it is not given a mode argument.

CLI (`cli.main`, `python -m wearable_pipeline`):

- `run [--data-dir data] [--output-dir output] [--mode {full,incremental}]`; `--mode` defaults
  to `full`. `--mode full` (or omitted) calls `run_pipeline` exactly as before and prints exactly
  the one existing line `run_id=<id> database=<path> report=<path>`. An unknown mode is an
  argparse error (exit 2).
- `--mode incremental` calls `run_incremental` with the default study window and prints
  `run_id=<id> database=<path> report=<path> mode=<outcome>`; when `fallback_reason` is set it
  prints a second line `fallback: full rebuild (<fallback_reason>)`. Exit 0, or 1 with
  `error: <message>` on stderr (and nothing on stdout) for `PipelineError`.
- `compare LEFT RIGHT` (two positional output directories), section 8.

## 2. Stored state used for change detection

The output database already stores `raw_manifest(relative_path, source, size_bytes, sha256,
record_count)`. The previous manifest is that table; the current manifest is built exactly as
today (every file is read and hashed, so a changed file is found by checksum; "not re-read"
below means *not parsed*). Three side tables are written by **every** run (full and
incremental), so a full rebuild and an incremental run always agree on them:

- `run_window(study_start DATE, study_days INTEGER)`: exactly one row, the study window of the
  run that last wrote the database (revision 2, decision D17). Window changes are detected by
  comparing it with the requested window; the gold dates are never used for this. A no-op
  run does not rewrite it (it is already equal).
- `quality_file_counts(relative_path VARCHAR, source VARCHAR, rule_id VARCHAR, checked_count
  BIGINT, failed_count BIGINT)`: for each sleep, steps and heart-rate file, one row per rule of
  its source (including `failed_count = 0`); `checked_count` is that file's record count.
- `silver_file_owners(relative_path VARCHAR, silver_table VARCHAR, participant_id VARCHAR)`:
  the distinct `participant_id` values carried by the silver rows that file produced, per silver
  table (`silver_sleep_sessions`, `silver_sleep_stages`, `silver_steps_minute`,
  `silver_heart_rate_minute`). It makes silver rows attributable to a file even when a record's
  `participant_id` differs from its folder.

Both are compared by the compare command like any other table.

## 3. Change detection and classification

`diff_manifests(previous, current)` classifies each path of the union: `new` (only in current),
`removed` (only in previous), `changed` (both, different sha256), `unchanged`. Results are sorted.

Each non-unchanged path is then classified by `raw_manifest.source`:

- **shared inputs**: `participants`, `wellness_survey`, `device_metadata`. Any new, changed or
  removed shared path, or a requested study window (`study_start`, `study_days`) different from
  the one stored in `run_window`, triggers a rebuild of every layer (section 6).
  Stale gold rows (kept by full mode after a window change) and an empty gold table do not make
  the window "changed": with unchanged inputs and an equal stored window the run is a no-op.
- **event files**: `sleep`, `steps`, `heart_rate` (`wearable_events/<folder>/<name>.json`):
  section 4.
- **other** (`documentation`, `unclassified`): affect only `raw_manifest`, the run id and the
  report; no layer is recomputed.

## 4. Event-file path (outcome `incremental`)

1. Parse only new and changed event files with `incremental.read_event_file`
   (same errors as full mode: `PipelineError` for unreadable, invalid UTF-8 JSON, a top level
   that is not an array, or a non-object element). Unchanged and removed files are never parsed.
2. For each parsed file call the existing `build_*_layer` with a one-file mapping, the enrolled
   ids (`participant_id` of `silver_participants`) and the window. This yields the file's silver
   rows, rejects, `failed` counter, `checked` count and per-day gold values.
3. Silver replacement, per source and silver table: delete the rows owned by changed and removed
   files (their `silver_file_owners` participants), then insert the rows of the fresh parse.
   Ownership is by participant: the participants of a file are its previous owners plus the
   participants of its fresh rows. If any such participant is also owned by another file of the
   same source and table (a record whose `participant_id` differs from its folder; for sleep
   also a `(participant_id, date)` session present in two files), the whole source is
   re-parsed from all its remaining files (new, changed and unchanged, never removed ones, each
   through `read_event_file`) and replaced; no other source is parsed. This is required for
   correctness, not only deletion. Verified against the builders: `build_sleep_layer` counts
   `(participant_id, date)` across all files (`SLEEP_DUPLICATE_PARTICIPANT_DAY` and the
   `is_duplicate_key` flag, orphan/gold contribution), so a change in one file alters the
   other file's rows; `build_steps_layer` and `build_heart_rate_layer` take the participant
   from the record, exclude folder-mismatch records from duplicate groups, and produce rows
   owned by a participant of another folder, which a per-file replacement would delete or
   keep wrongly. Output still equals a full rebuild. Without such shared ownership only the
   changed file is parsed.
4. Rejects: delete `quality_rejects` rows whose `row_ref` starts with `<path>:` for each changed
   and removed path; insert the new file's rejects. Every remaining row's `run_id` is rewritten
   to the new run id. `quality_file_counts` and `silver_file_owners` rows of changed and removed
   files are replaced or deleted likewise.
5. `quality_results` is rebuilt: for each rule, `failed_count` is the sum over files of
   `quality_file_counts.failed_count`, plus, for the participants and survey rules, the stored
   `quality_results` value (their inputs are unchanged on this path). `checked_count` is the sum
   likewise per source. Rows, ordering and `run_id` are those of a full rebuild.
6. `raw_manifest` is replaced by the current manifest; the report is rendered from the rebuilt
   `quality_results` with the existing report format.

Every one of the tables above must equal what `run_pipeline` gives into a fresh output
directory; this equivalence (not the steps above) is the contract. The steps are the
planner's design.

## 5. Fallbacks and no-op

Checked in this order on the existing output directory:

1. no `wearable.duckdb`: full rebuild, `fallback_reason = "no_database"`.
2. `raw_manifest` missing or empty: full rebuild, `"no_manifest"`.
3. **old schema**: any of `raw_manifest`, `silver_participants`, `silver_wellness_survey`,
   `silver_sleep_sessions`, `silver_sleep_stages`, `silver_steps_minute`,
   `silver_heart_rate_minute`, `quality_results`, `quality_rejects`, `quality_file_counts`,
   `silver_file_owners`, `run_window`, `gold_clinical_daily` is missing, or has a column list
   (names, types, order)
   different from what the current pipeline creates (gold: the 28 columns of INC-005):
   full rebuild, `"old_schema"`.
4. Otherwise shared change or window change: outcome `full`, `"shared_input_changed"` or
   `"window_changed"` (section 6).
5. Nothing new, changed or removed: outcome `noop`: no table, file or run id is touched; the
   database is not opened for writing; `affected_gold_rows = 0`; `fallback_reason = None`.
6. Otherwise outcome `incremental` (also when only "other" files changed; then
   `affected_gold_rows = 0` and only `raw_manifest`, run ids and the report change).

Fallbacks 1 to 3 run exactly `run_pipeline` (so gold keeps its MERGE semantics: stale rows are
retained). A column whose type or position differs, as well as a missing table or column, is
`old_schema`; a name-only comparison is not enough. A corrupt database file raises
`PipelineError` and is not modified. `run_pipeline` (all modes) writes `run_window`; `run_window`
missing or not exactly one row is `old_schema`.

## 6. Gold recompute and MERGE

Event-file path. For each affected source and participant, `changed_days(previous_silver_rows,
new_silver_rows)` gives the local dates whose multiset of silver rows differs, over every silver
table of that source (rows with a NULL date are ignored). The previous rows are read from the
database before deletion, the new rows from the fresh parse. For each affected
(`participant_id`, `local_date`) that already has a `gold_clinical_daily` row, the staged row is
that existing row with only that source's gold columns replaced by the fresh values
(sleep: 6, steps: 6, heart rate: 6 columns, as in `pipeline._*_gold`); a day without records in
the fresh parse gets the documented no-record values (NULL aggregates, counts 0, presence false,
NULL flags). Staged rows are MERGEd on (`participant_id`, `local_date`), the same statement form
as full mode. Days with no existing gold row (non-enrolled participant, day outside the window)
are never inserted. A corrected single record therefore changes exactly one gold row.
`affected_gold_rows` is the number of (participant, day) rows staged.

Shared-input or window change (outcome `full`, `fallback_reason` `shared_input_changed` or
`window_changed`): all layers are recomputed in memory from all files as in full mode, written in
one transaction, and `gold_clinical_daily` is MERGEd and then pruned: rows whose key is not in
the staged enrolled-participants x window set are deleted, so the result equals a fresh full
rebuild even when a participant was removed. (Full mode itself keeps retaining stale gold rows;
only this incremental path prunes.)

## 7. Transactions, failure and determinism

- Everything that changes the database (silver, rejects, quality tables, side tables, manifest,
  gold MERGE and prune, `DerivedTable.refresh`) runs in one DuckDB transaction. Any exception,
  including exceptions raised by a derived table, rolls it back and propagates unchanged
  (DuckDB errors are wrapped in `PipelineError`; `PipelineError` and others are not altered).
- Parsing, validation and the report text are done before the transaction opens; a failure
  there leaves the output directory byte-identical (no database file is created or opened for
  writing).
- The report is written to a temporary file in `quality/` and moved over `report.md` only after
  the transaction commits; a failed run leaves `report.md` and the directory listing unchanged.
- No wall-clock time, random values or machine paths appear in any output. Two identical
  histories (inputs and runs) give identical tables; repeating an incremental run is a no-op.
- Raw files under `data_dir` are never modified and nothing is created there.

## 8. Compare command

`compare_outputs(left: Path, right: Path) -> CompareResult`, never writes. Each output directory
must contain `wearable.duckdb`, opened `read_only=True` (no `.wal` or other file is created);
otherwise `PipelineError` (unreadable directory, missing database, corrupt database, a file
instead of a directory). Behavior:

- Tables: every base table in schema `main` of each database, discovered at run time (no name
  list). A table in only one database: `TableDiff(status="missing_left" | "missing_right")`.
- Columns: the ordered `(name, type)` list must match, else `status="columns"` and `columns` lists
  (sorted) the names present on one side only or typed differently; rows are then not compared.
- Rows: multisets compared independent of order (NULL equals NULL, exact value equality, e.g.
  `EXCEPT ALL` in both directions). A difference gives `status="rows"` with `left_rows`,
  `right_rows`, `left_only_rows`, `right_only_rows`.
- Reports: every regular file under `<dir>/quality/` (relative path, recursively) must exist on
  both sides with byte-identical content; else a `(relative_path, "differs" | "missing_left" |
  "missing_right")` entry. Paths are POSIX style, e.g. `quality/report.md`.
- `identical` is true only when there are no table and no report differences.
  `table_diffs` is sorted by table name, `report_diffs` by path.

`format_comparison` output (stdout, `\n` line endings, final newline):

```
identical
```
or
```
differ
table <name>: missing in left|right
table <name>: columns differ: <name>,<name>
table <name>: rows differ: left_rows=<n> right_rows=<n> left_only=<n> right_only=<n>
report <relative path>: differs|missing in left|missing in right
```
Table lines are in name order, then report lines in path order. Only table names, column names,
relative report paths and counts are ever printed; never a row value, participant id or
checksum.

CLI `compare LEFT RIGHT`: prints `format_comparison` to stdout and exits 0 when identical, 1 when
they differ. When an output cannot be read it prints `error: <message>` to stderr, nothing to
stdout, and exits 1. A wrong argument count is an argparse error (exit 2).

## 9. Extension point for INC-007 and INC-008

```python
class DerivedTable(Protocol):
    name: str
    def refresh(self, con: duckdb.DuckDBPyConnection,
                affected: Mapping[str, frozenset[date]] | None) -> None: ...
DERIVED_TABLES: list[DerivedTable]   # module-level, empty in this increment
```

- `incremental.DERIVED_TABLES` is read at call time (not copied at import), by both
  `run_incremental` and `run_pipeline`, so tests and later increments may replace or extend it.
- After gold is brought up to date and inside the same open transaction, each registered table's
  `refresh` is called once, in list order. `affected` maps `participant_id` to the dates whose
  `gold_clinical_daily` row was recomputed in this run, or is `None` meaning "rebuild entirely"
  (any `run_pipeline` call, any fallback, any shared-input or window change).
- A no-op run does not call `refresh`. A run whose event-file change affects no gold row either
  skips the call or passes an empty mapping.
- Tables created by `refresh` are covered by the compare command by name discovery; a raised
  exception rolls back the whole run (section 7).
- `run_pipeline` gains the call `refresh(con, None)` inside its transaction; with the empty
  default list its behavior is unchanged.

## 10. Quality rules

None added. No new rule ids, rejects or report columns. Quality tables and the report after an
incremental run are those of a full rebuild on the same inputs (global counts, section 4).

## 11. Verification gates

- `python -m pytest -q` passes (new: `tests/test_incremental.py`, `tests/test_compare.py`).
- Equivalence: after each of {new day appended, record corrected, record removed, file removed
  (steps, sleep, heart rate), participant or survey or device metadata change, new participant file,
  defects, orphan folder, folder/participant mismatch, study window change, other-file change} an
  incremental run equals a fresh full rebuild in every table and in the report bytes.
- Reads: only new and changed event files reach `read_event_file`; a no-op reads none. When a
  participant is owned by two files of one source (sleep `(participant, date)` in two files;
  folder-mismatch records in steps or heart rate) the whole source (remaining files) is parsed
  and the result equals a full rebuild, for a change in either file and for a removal of either.
- Window: `run_window` is written by every run; stale or empty gold with unchanged inputs and
  window gives a no-op; a different requested window gives `window_changed` and equals a full
  rebuild; the gold dates are never used to infer the window.
- Old schema: a missing table or column, a changed column type and a changed column order each
  fall back with `old_schema`.
- Affected rows: gold rows that differ before and after are exactly the affected participant-days,
  and `affected_gold_rows` is the number of (participant, day) pairs with a gold row whose silver
  rows changed (explicit sets are fixed for the defects, orphan folder, folder mismatch and
  sleep participant-differs cases).
- No-op, fallbacks, rollback, determinism, CLI surface and compare behavior as in sections 5 to 8.
- Real-data evidence (human, on a copy of `data/`) as listed in the intent; `data/` hash unchanged.

## 12. Examples

Full run, then P001's `heart_rate.json` has one bpm corrected on 2026-01-08:
`diff_manifests` gives `changed = ("wearable_events/P001/heart_rate.json",)`; one file is parsed;
`changed_days` over `silver_heart_rate_minute` rows of P001 gives `{2026-01-08}`; one gold row is
staged and MERGEd; `quality_results` counts are unchanged except as the corrected record alters
them; `run_id` changes; stdout:
`run_id=<16 hex> database=output/wearable.duckdb report=output/quality/report.md mode=incremental`.

Compare of two identical outputs: stdout `identical`, exit 0. A changed fatigue score in one gold
row of the right output:
```
differ
table gold_clinical_daily: rows differ: left_rows=6 right_rows=6 left_only=1 right_only=1
```
exit 1.
