## 2. Data contract: inputs

Gold tables only (names and columns are imported from the code by the tests, not copied):

- `gold_chronotype_cohort`, one row per enrolled participant, key `participant_id`
  (`cohort.COHORT_COLUMNS`): `chronotype_cohort` (`A`, `B` or NULL), `cohort_flag`,
  `window_days`, `sleep_valid_days`, `sleep_stage_valid_days`, `steps_valid_days`,
  `hr_valid_days`, `sleep_total_min_mean`, `sleep_efficiency_pct_mean`, `deep_sleep_pct_mean`,
  `steps_daily_mean`, `hr_daily_mean_bpm`. A mean is NULL below 14 valid days (INC-008).
- `gold_clinical_daily`, one row per `(participant_id, local_date)` (`pipeline.ALL_GOLD_COLUMNS`);
  used columns: `total_steps`, `total_sleep_min`, `hr_mean_bpm` (NULL when the day has no valid value).

`gold_biostat_weekly` is not read by any query.

## 3. Data contract: SQL files and result grain

Two files, each one `SELECT`/`WITH` statement (optional trailing `;`, comments allowed), with an
explicit `ORDER BY`. No DDL/DML, no `silver_*`, `bronze`, `quality_*`, `raw_manifest` or file
readers. Exactly these two `*.sql` files exist in `queries/`.

### 3.1 `queries/chronotype_comparison.sql` (reads only `gold_chronotype_cohort`)

Grain: exactly three rows, always present, in this order: `group_label` = `A`, `B`, `A_minus_B`.
Columns (21, in this order): `group_label`, then for each metric in the order
`sleep_total_min`, `sleep_efficiency_pct`, `deep_sleep_pct`, `steps_daily`, `hr_daily_bpm` the four columns
`<m>_mean`, `<m>_participants`, `<m>_stddev`, `<m>_valid_days`.

| metric | source mean column | valid-day column |
|--------|--------------------|------------------|
| `sleep_total_min` | `sleep_total_min_mean` | `sleep_valid_days` |
| `sleep_efficiency_pct` | `sleep_efficiency_pct_mean` | `sleep_stage_valid_days` |
| `deep_sleep_pct` | `deep_sleep_pct_mean` | `sleep_stage_valid_days` |
| `steps_daily` | `steps_daily_mean` | `steps_valid_days` |
| `hr_daily_bpm` | `hr_daily_mean_bpm` | `hr_valid_days` |

- Cohort A / B rows use the participants with `chronotype_cohort` = `A` / `B`; participants with a NULL
  cohort are in neither row. Per metric, only participants whose mean is NOT NULL contribute:
  `_mean` = average of those participant means (mean of participant-level means), `_participants` = their
  count, `_stddev` = **sample** standard deviation (n-1) of those means (NULL when fewer than 2),
  `_valid_days` = sum of the valid-day column of those same participants.
- A cohort with no contributing participant: `_participants` = 0, `_valid_days` = 0, `_mean` and `_stddev` NULL.
  The row is still output (also for an empty table).
- `A_minus_B` row: `_mean` = (unrounded A mean) minus (unrounded B mean), NULL if either is NULL;
  `_participants`, `_stddev` and `_valid_days` are NULL. Positive means A is higher. No significance test,
  p-value or "significant" wording anywhere.
- Rounding: `_mean` and `_stddev` are `ROUND(..., 2)` as the last step; counts and valid days are integers.

### 3.2 `queries/study_wide_metrics.sql` (reads only `gold_clinical_daily`)

Grain: three rows in this order: `metric` = `steps_per_day`, `sleep_total_min`, `hr_mean_bpm`.
Columns: `metric`, `participants`, `valid_days`, `mean_of_participant_averages`.

- A valid day of a metric is a `gold_clinical_daily` row whose source (`total_steps`, `total_sleep_min`,
  `hr_mean_bpm`) is NOT NULL: the same notion as the cohort table's `*_valid_days` (steps/sleep/heart rate).
- Participant average = mean of the participant's valid-day values; the study value is the mean of the
  participant averages (not the pooled mean of all days). `participants` counts participants with at least one
  valid day, `valid_days` sums their valid days. `ROUND(..., 2)`. Empty input gives 0, 0, NULL for every row.
- No coverage threshold (the cohort table's 14-day rule does not apply) and no cohort filter: every
  participant in `gold_clinical_daily` counts. The two tables therefore differ by design (P5).

## 4. Query runner (`wearable_pipeline.query_runner`)

Contract (stub exists; bodies raise `NotImplementedError`): `DEFAULT_DATABASE = Path("output/wearable.duckdb")`,
`DEFAULT_SQL_PATH = Path("queries")`, `QueryRunnerError`, frozen dataclass `QueryResult(name, columns, rows)`,
`collect_sql_files(sql_path)`, `run_queries(database, sql_path)`, `format_results(results)`, `main(argv)`.

1. **CLI**: `python -m wearable_pipeline.query_runner [SQL_PATH] [--database PATH]`; defaults above.
   Not a pipeline subcommand; `cli.py`, `__init__.py` and `__main__.py` are unchanged.
2. **Files**: a file is run as given (any name); a directory runs its `*.sql` files, non-recursive, sorted by
   file name. One statement per file; a comment-only/empty file is an error.
3. **Output** (`format_results`), per result: `# <file name>`, a pipe table header, a `| --- |` separator and
   one line per row; NULL prints `NULL`, other values `str(value)`. Results are separated by one blank line; the
   text ends with one newline; no results gives `""`. All queries run before anything is printed.
4. **Read-only**: the database is opened with `read_only=True`; a missing database is never created; no
   table, file or WAL is created; a write statement fails like any invalid query. The directory is byte-identical
   after a run.
5. **Exit behavior**: 0 on success. Exit 1, nothing on stdout, one `error: <message>` line on stderr, no
   traceback: `database not found: <path>`; `sql path not found: <path>`; `no .sql files in <dir>`;
   `query failed in <file name>: <DuckDB message>`; an empty SQL file names the file. Argparse usage errors exit 2.
6. Deterministic: same database gives identical text on every run (explicit `ORDER BY`).

## 6. Quality rules

- Gold-only reads: static (table identifiers after `FROM`/`JOIN` are `gold_*` or CTEs; no forbidden prefixes) and
  behavioral (each query runs on a database containing only its own gold table).
- NULL handling: NULL means are excluded from counts, valid days and stddev; NULL days are not valid days.
- Idempotent and read-only: reruns give identical output; the database file is never changed.
- Real-data checks (human, section 8) cover what fixtures cannot.

## 9. Planning decisions (gate G3: P1-P12 ratified by the human on 2026-10-14; P8 as stated below, the rest unchanged)

Human rulings at G3: `gold_participant_devices` stays not implemented (P8 as planned: the README records it as a client requirement the pipeline does not produce, never as delivered in INC-002; this supersedes the contrary line in the committed intent, which the human may amend). The exact `compare` command is the form in `specs/INC-009.md` (P10).

- **P1 Two query files**, names `chronotype_comparison.sql` and `study_wide_metrics.sql`; each reads one gold
  table. Alternative: one combined file (rejected: separate files are what the intent asks).
- **P2 Wide chronotype layout** (3 rows x 21 columns) because the intent asks for rows A, B and A minus B.
  Alternative: long layout, one row per group and metric (easier to print, but loses the three-row grain).
- **P3 Sample standard deviation** (n-1), NULL for one participant; population SD rejected because participants
  are a sample of the cohort. Both are over participant means.
- **P4 Rounding** to 2 decimals in SQL (last step; the difference uses unrounded means), so captured output is
  readable and exactly comparable. Alternative: unrounded floats in SQL, rounding only in the runner.
- **P5 Valid days**: a valid day is a non-NULL daily value; the study-wide query has no 14-day coverage rule and
  no cohort filter, so participants below the cohort threshold or without a cohort still count. The cohort
  table's valid days are summed only over participants whose mean is non-NULL (consistent with the counts).
- **P6 Sign** A minus B (positive = A higher); `participants`, `stddev` and `valid_days` are NULL on that row.
- **P7 Runner**: positional `SQL_PATH` (default `queries`) and `--database` (default `output/wearable.duckdb`);
  exit 1 with `error:` on stderr and empty stdout for a missing database, missing path, no SQL files, an empty or
  failing query; no partial output; usage errors exit 2. Output format as in section 4.3.
- **P8 `gold_participant_devices` conflicts with the intent.** The intent says it was delivered in INC-002 (and
  INC-008's intent says "already produced"), but no code, schema or test defines it (`grep` of `src/` and
  `tests/` finds none; INC-002's spec and report list it as out of scope; `device_metadata.csv` only reaches
  `raw_manifest`, and `device_id` is a `silver_participants` column). Tests therefore require the README to
  record it as a client requirement the pipeline does **not** produce and forbid "delivered in INC-002". If the
  human wants it stated as delivered, a code increment must create the table first, or the intent must change.
- **P9 Fixtures** are built in `tmp_path` DuckDB files with the real column lists imported from the code
  (`cohort.COHORT_COLUMNS`, `pipeline.ALL_GOLD_COLUMNS`); only gold tables exist in them. README cross-check
  derives known names from the code (`pipeline.TABLE_DDL`, weekly and cohort columns, module and script names)
  and skips the two preserved sections. Rule: backticked `gold_*`/`silver_*`/`quality_*`/`raw_manifest` names
  must be tables, `table.column` must exist, other snake_case spans must be a known name.
- **P10 README structure** and diagram layout as in section 5; heading names are pinned by tests. The compare
  command is the form of `specs/INC-009.md` section 4 (second directory mounted with `-v`); the INC-009 evidence
  report records that `compare` was run but not its exact command line, so the human should confirm it.
- **P11 Preserved sections are pinned** by key lines, so a factual correction to them needs a test change.
- **P12 Evidence gaps**: INC-009 recorded the database size (19.4 MB) but no raw dataset size, so Scaling uses
  that. The reports show the heredoc slip in `reports/INC-006/implementer.md` (a `/tmp` file) and a script-edit
  slip in `reports/INC-007/planner.md`; the intent speaks of heredoc appends to the INC-006/INC-007 evidence
  reports, which the planner could not confirm. The README must use wording the human confirms.
