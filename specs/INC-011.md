## 1. Profile of the real inputs (observed vs assumed)

Observed (profiling of `participants/participants.csv` and `health_summaries/device_metadata.csv`):

- 50 participants (P001-P050), 50 distinct `device_id`, one metadata row each; both files carry the same 50 participant ids and the same 50 device ids, with no mismatch and no shared device.
- Every `device_id` matches `FBT-NNNN-XXXXXXXX` with `XXXXXXXX` = 8 uppercase hex characters.
- `firmware_version`: `2.2.0` x23, `2.2.1` x12, blank x15. All 15 blank rows carry `fw<major.minor.patch>` in `device_label` (e.g. `Fitbit Charge 5 · fw2.1.8 · SN:FBT-0006-6D2D9CBD`); the 35 non-blank rows never disagree with their label.
- `device_metadata.csv` columns: `participant_id, device_id, wear_site, calibration_date, firmware_version, device_label`.

Assumed (not provable from the data): the id pattern uses `[A-Z0-9]{8}` (the dictionary only says `XXXXXXXX`; all observed values are hex); a non-blank `firmware_version` column wins over the label (observed zero conflicts, so not flagged); a version token is dotted numeric (`fw` + digits and dots).

## 2. Data contract

### Inputs

| File | Grain | Key |
|---|---|---|
| `participants/participants.csv` | one row per enrolled participant (may repeat; see rule PARTICIPANTS_KEY_DUPLICATE) | `participant_id` |
| `health_summaries/device_metadata.csv` | one row per device | `participant_id` (join), `device_id` (cross-check) |

`device_metadata.csv` is now a **required** input: a missing file fails the run with `required input missing: health_summaries/device_metadata.csv`, and missing `participant_id` or `device_id` columns fail with `... is missing required columns: ...` (same `PipelineError` path as `participants.csv`), before any table is touched. `firmware_version` and `device_label` columns are optional: when absent they read as blank. Rows are matched on `participant_id` with exact string equality; no trimming of ids.

### `silver_device_metadata` (new, in `pipeline.TABLE_DDL`)

Grain: one row per `device_metadata.csv` row (file order is not significant; rows for unenrolled participants are kept). Columns in order:

| Column | Type | Meaning |
|---|---|---|
| `participant_id` | VARCHAR | raw |
| `device_id` | VARCHAR | raw |
| `firmware_version_raw` | VARCHAR | raw column value, untrimmed, `''` if blank or column absent |
| `device_label` | VARCHAR | raw, `''` if absent |
| `firmware_version_parsed` | VARCHAR | derived: first label match of `FIRMWARE_PATTERN`, else NULL (always computed, even when unused) |
| `firmware_version` | VARCHAR | final: stripped raw value if not blank, else parsed value, else NULL |
| `firmware_source` | VARCHAR | derived marker: `metadata`, `device_label` or `none` |
| `quality_flags` | VARCHAR | `FIRMWARE_RECOVERED_FROM_LABEL` when source is `device_label`, `FIRMWARE_UNRECOVERABLE` when `none`, else NULL |

Firmware pattern: `(?<!\w)fw(\d+(?:\.\d+)+)(?!\w|\.\d)` (case-sensitive; first match). "Blank" means empty or whitespace only. `fw2` (no dot), `FW2.2.1`, `softfw2.2.1` and `fw2.2.1a` do not match.

### `gold_participant_devices` (new)

Grain: one row per distinct `participant_id` in `participants.csv` (the enrolment checks of the pipeline are those of `silver_participants`: every listed participant is enrolled). Columns, exactly, in order: `participant_id VARCHAR`, `device_id VARCHAR`, `firmware_version VARCHAR`. Key: `participant_id` (unique). Ordering of rows is not significant; the layer returns them sorted by `participant_id`.

- `device_id`: the raw `participants.csv` value of the **first listing** of the participant (authoritative link; kept as is even if blank or malformed).
- `firmware_version`: `silver_device_metadata.firmware_version` of the **chosen metadata row**; NULL when no row exists or none resolves. The chosen row is the first row (file order) of that `participant_id` whose `device_id` equals the participant's `device_id`; if none matches, the first row of that participant; if the participant has no row, there is none.
- No date or time semantics: the table is not tied to the study window.
- Gold carries no flag column (the intent fixes three columns); findings live in `quality_results`, `quality_rejects` and `silver_device_metadata.quality_flags`.

## 3. Quality rules

Five rules, source `device_metadata`, added to `pipeline.RULES` (from `devices.DEVICE_RULES`). All are evaluated per participant: `checked_count` = number of distinct `participant_id` values in `participants.csv` (the gold row count), `failed_count` = participants failing the rule. Every participant still appears in gold; nothing is excluded or defaulted.

| rule_id | handling | severity | Fails when |
|---|---|---|---|
| `DEVICE_ID_MISMATCH` | flag | high | no metadata row of the participant has the same `device_id` (including no row at all) |
| `DEVICE_SHARED` | flag | high | the participant's `device_id` is used by another distinct `participant_id` (both participants fail) |
| `DEVICE_ID_MALFORMED` | flag | medium | `device_id` does not `fullmatch` `FBT-\d{4}-[A-Z0-9]{8}` (blank included) |
| `FIRMWARE_RECOVERED_FROM_LABEL` | convert | low | the chosen row has blank firmware and the label gave a version |
| `FIRMWARE_UNRECOVERABLE` | flag | medium | gold `firmware_version` is NULL (blank and no label version, or no metadata row); it stays NULL |

Exact reason texts are `devices.DEVICE_RULES[rule][3]` (also pinned in `tests/test_walking_skeleton.py::DEVICE_REASONS`).

**Run failure**: none of the five rules fails the run (decision P1). Only a missing file or missing required column does. 

**Rejects** (`quality_rejects`, existing layout, `source = device_metadata`): one row per failing participant per rule, `run_id`, `rule_id`, `row_ref = "<relative path>:<1-based data row>"`, `raw_values = json.dumps(raw CSV row dict, ensure_ascii=False)`. Evidence row: for `DEVICE_SHARED` and `DEVICE_ID_MALFORMED` the participant's first `participants.csv` row; for the other three the chosen `device_metadata.csv` row, or the participant's first `participants.csv` row when there is no metadata row. Raw values are never altered.

**Report**: `quality/report.md` lists the five rules like all others (`| rule_id | source | handling | severity | checked | failed |`). Total rules: 41 -> 46.

## 4. Run behaviour

- Full run (`run_pipeline`, and `run_incremental` when it falls back): `_run_full` reads `device_metadata.csv`, builds the layer with `build_device_layer(participants, metadata)` and, in `_persist`'s transaction, replaces `silver_device_metadata` and `gold_participant_devices` (`_replace` strategy: the table is tiny and the whole grain is rebuilt; no row survives from an earlier run). Rule counts are added to `t["failed"]`, `t["checked"]["device_metadata"]` and the rejects to `t["rejects"]`.
- Incremental mode: `participants.csv` and `device_metadata.csv` already belong to `_SHARED_SOURCES`, so any change to either takes the existing `shared_input_changed` full rebuild; an unchanged input leaves the device tables untouched (no-op or event-only run). `_EXPECTED_TABLES` and `_expected_schema` include `gold_participant_devices` and `silver_device_metadata` (the latter through `TABLE_DDL`), so an output created before this increment is rebuilt in full with reason `old_schema`. `quality_results` of the device rules is carried over from the previous run on incremental runs (like the other shared-source rules).
- `compare` needs no code change: it already compares every base table of both databases; the new table is covered (tested).
- Idempotent: identical inputs give identical tables, same `run_id`; a rerun in the same directory changes nothing and never duplicates rows. A changed input updates, adds and removes rows to equal a fresh full run.
- No change to existing schemas, keys, `run_id`, CLI commands, or `pyproject.toml`/`uv.lock`.

## 10. Planning decisions (need ratification)

- P1 No device finding fails the run; all are flagged in the quality report. A missing `device_metadata.csv` or required column does fail.
- P2 `device_metadata.csv` becomes required (columns `participant_id`, `device_id`); optional `firmware_version`/`device_label`. This is a behaviour change for runs lacking the file; existing fixtures all provide it.
- P3 Firmware regex above; non-blank metadata value wins; label disagreement is not a finding (zero observed).
- P4 Silver stores raw, parsed, final and source; gold stores only the final value. Gold has no flag column.
- P5 `device_id` pattern `FBT-\d{4}-[A-Z0-9]{8}`.
- P6 Derivation lives in a pure builder in `devices.py` (not a gold SQL query); gold written by `_persist` with `_replace`, not a `DerivedTable`, because both inputs are shared sources that always trigger a full rebuild.
- P7 Quality rules are participant-level with `checked_count` = participants; a participant with no metadata row counts as mismatch and as unrecoverable.
- P8 Duplicate participant listings: first listing wins; the existing `PARTICIPANTS_KEY_DUPLICATE` rule reports it.
- P9 Rule count rises 41 -> 46, which requires the amended existing assertions listed in section 6.
- P10 The intent names `reports/INC-011/`; the runner artifact id is `INC-011-participant-devices`, so the report is `reports/INC-011-participant-devices/planner.md`.
