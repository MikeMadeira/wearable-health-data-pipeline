# INC-008: Chronotype Cohort Table (`gold_chronotype_cohort`)

Status: Approved (decisions D1-D12 in section 12 ratified by the human at G3 on 2026-10-14)
Source intent: `intents/INC-008-chronotype-cohort.md`
Upstream decisions: `reports/INC-001/profiling-findings.md` Section 7, item 8 (all enrolled
participants are retained in chronotype cohorts A and B; metric-specific validity counts instead of
dropping participants; no imputation; missing steps are not zero; missing heart rate is not a
measured value; conflicting duplicates are omitted; coverage and valid counts are exposed).
Amends: `specs/INC-006.md` section 9 (`DERIVED_TABLES` is `[WEEKLY, COHORT]`) and section 5 (the
old-schema check also covers `gold_chronotype_cohort`), exactly as `specs/INC-007.md` did for the
weekly table. Everything not named here is unchanged: `run_pipeline`, `run_incremental`,
`compare_outputs`, the CLI, every existing table (including `gold_clinical_daily` and
`gold_biostat_weekly`), `run_id`, `quality_results`, `quality_rejects` and the report.

## 1. Public contract

New module `src/wearable_pipeline/cohort.py`:

| Name | Shape |
|------|-------|
| `TABLE_NAME` | `"gold_chronotype_cohort"` |
| `MIN_VALID_DAYS` | `14` (section 6) |
| `VALID_COHORTS` | `("A", "B")` |
| `FLAG_MISSING`, `FLAG_UNEXPECTED`, `FLAG_CONFLICT` | `"CHRONOTYPE_MISSING"`, `"CHRONOTYPE_UNEXPECTED"`, `"CHRONOTYPE_CONFLICT"` |
| `COHORT_COLUMNS` | ordered tuple of `(name, duckdb_type)`, section 3 |
| `classify_cohort(chronotypes: Sequence[str \| None]) -> tuple[str \| None, str \| None]` | pure; `(cohort, flag)` of one participant from the chronotype values of all its `silver_participants` listings, section 4 |
| `mean_if_covered(values: Sequence[float], minimum: int = MIN_VALID_DAYS) -> float \| None` | pure; `None` when `len(values) < minimum`, otherwise `sum(values) / len(values)` as a float |
| `ChronotypeCohort` | class implementing `incremental.DerivedTable`; `name == TABLE_NAME`; `refresh(con, affected) -> None` |
| `COHORT` | the single `ChronotypeCohort()` instance registered in `incremental.DERIVED_TABLES` |

`incremental.DERIVED_TABLES` is `[WEEKLY, COHORT]` (read at call time as today). `cohort` may import
`weekly` helpers; `weekly` must not import `cohort`; `cohort` must not import `incremental` (no
cycle: `incremental` imports `cohort`). No new runtime dependency. No CLI change: `run` and `compare`
discover tables by name.

## 2. Grain, key and population

- **Output grain:** one row per enrolled participant. Key `participant_id`, declared `PRIMARY KEY`
  and used for the MERGE.
- **Enrolled participants:** the distinct `participant_id` values of `silver_participants` (a
  participant listed twice in `participants.csv` yields one row). Orphans (ids present only in the
  event files or survey) never get a row. No enrolled participant is dropped for incomplete data: a
  participant with no data at all keeps a row (all counts 0, all means NULL).
- **Cardinality:** number of enrolled participants; 50 rows on the real data (A 28, B 22).
- **Window:** read from `run_window` (`study_start`, `study_days`) of the same database. The summary
  covers **every** day of the window (decision D6), including a trailing block shorter than seven
  days (unlike the weekly table). `window_days = study_days`.
- **Local dates** are the silver `local_date` values; no time-zone logic is added.

## 3. Schema

| # | Column | Type | Null | Meaning |
|---|--------|------|------|---------|
| 1 | `participant_id` | VARCHAR | NOT NULL | key |
| 2 | `chronotype_cohort` | VARCHAR | NULL allowed | `'A'` or `'B'`, else NULL (section 4) |
| 3 | `cohort_flag` | VARCHAR | NULL allowed | NULL when the cohort is set; else `CHRONOTYPE_MISSING`, `CHRONOTYPE_UNEXPECTED` or `CHRONOTYPE_CONFLICT` |
| 4 | `window_days` | INTEGER | NOT NULL | `study_days` of the run |
| 5 | `sleep_valid_days` | INTEGER | NOT NULL | days with a non-NULL daily total sleep minutes |
| 6 | `sleep_stage_valid_days` | INTEGER | NOT NULL | days with a non-NULL daily deep-sleep share (equally: efficiency) |
| 7 | `steps_valid_days` | INTEGER | NOT NULL | days with a non-NULL daily total steps (a zero-step day is valid) |
| 8 | `hr_valid_days` | INTEGER | NOT NULL | days with at least one valid heart-rate minute |
| 9 | `sleep_total_min_mean` | DOUBLE | NULL allowed | mean of daily total sleep minutes over `sleep_valid_days` |
| 10 | `sleep_efficiency_pct_mean` | DOUBLE | NULL allowed | mean of daily stage-derived efficiency over `sleep_stage_valid_days` |
| 11 | `deep_sleep_pct_mean` | DOUBLE | NULL allowed | mean of daily deep-sleep share over `sleep_stage_valid_days` |
| 12 | `steps_daily_mean` | DOUBLE | NULL allowed | mean of daily total steps over `steps_valid_days` |
| 13 | `hr_daily_mean_bpm` | DOUBLE | NULL allowed | mean of the daily mean heart rate over `hr_valid_days` |

The table shares only `participant_id` with `gold_clinical_daily` (no `local_date`, no daily column
name; test: name intersection with the daily table is `{"participant_id"}`). Measure names intentionally
repeat weekly names (`sleep_total_min_mean`, ...) with the same meaning at participant grain.
Coverage columns 4-8 are never NULL (`0` = no valid data). Columns 9-13 are NULL when their own valid-day
count is below `MIN_VALID_DAYS`; the table never stores 0 for "no data".

## 4. Cohort attribute (D1, D2)

Source: `silver_participants.chronotype` (raw string; the silver table is unchanged). Inputs of
`classify_cohort`: the chronotype values of every listing of one participant, in any order.

1. Values that are NULL or empty/whitespace-only are *missing* and are ignored when another listing has
   a value.
2. Let `present` be the distinct non-missing values (compared exactly: no trimming, no case folding).
3. `present` empty (no listing, or all missing) -> `(None, FLAG_MISSING)`.
4. More than one distinct present value (for example `A` and `B`, or `A` and `Z`) -> `(None, FLAG_CONFLICT)`
   (the rows disagree; a cohort is never invented).
5. Exactly one present value: `A` or `B` -> `(value, None)`; anything else (`Z`, `a`, ` A`) ->
   `(None, FLAG_UNEXPECTED)`.

The flag is a column of this table only; no quality rule, `quality_results`/`quality_rejects` row or report
text is added. The participant keeps its row and its measures whatever the cohort.

## 5. Source and per-day values (silver, not gold) (D7)

`ChronotypeCohort.refresh` reads **only** silver tables and `run_window`, never `gold_clinical_daily`
(test: altering gold values then running `refresh(con, None)` leaves the cohort rows unchanged). It
derives, per participant and local date of the window, exactly the values the daily builders put in
`gold_clinical_daily`: the day scope, sleep day (distinct-metric-set rule and the stage-to-session
attribution), steps day, heart-rate day, folder-mismatch exclusion, exact-duplicate-counts-once and
conflicting-duplicate-is-missing rules of `specs/INC-007.md` section 4. The implementation must reuse the
INC-007 per-day derivation (importing `weekly` helpers or moving them to a shared private module, with no
change to weekly behaviour) so cohort, weekly and daily values cannot drift. Orphan, undated, out-of-window
and folder-mismatch rows never contribute. The survey is not used (no survey measure in this table).

A day is **valid** for a measure when its daily value is non-NULL: sleep -> `total_sleep_min`; sleep stage
measures -> `deep_sleep_pct` (equally `sleep_efficiency_pct`); steps -> `total_steps`; heart rate -> at least
one valid minute (`hr_valid_minute_count > 0`). Flags do not invalidate a day (the daily withheld-value
rules already removed what is unusable).

## 6. Statistics and coverage threshold (D3, D4, D5)

For one participant, over the days of the whole window only; missing days and minutes are absent, never
imputed, and a missing day is never a zero day:

| Measure | Statistic | Gate |
|---------|-----------|------|
| `sleep_total_min_mean` | mean of daily `total_sleep_min` over valid sleep days | `sleep_valid_days` |
| `sleep_efficiency_pct_mean`, `deep_sleep_pct_mean` | mean of daily `sleep_efficiency_pct`, `deep_sleep_pct` over stage-valid days | `sleep_stage_valid_days` |
| `steps_daily_mean` | mean of daily `total_steps` over valid step days (zero-step days included, missing days excluded) | `steps_valid_days` |
| `hr_daily_mean_bpm` | mean of daily `hr_mean_bpm` over days with a valid minute, **each valid day weighted equally** (not minute-weighted) | `hr_valid_days` |

**Heart-rate definition (D5):** the participant value is the mean of the daily means (`gold_clinical_daily.hr_mean_bpm`
of the valid days), as the intent requires equal weight per valid day. This intentionally differs from
`gold_biostat_weekly.hr_weekly_mean_bpm`, which is minute-weighted. Example: 15 days with one valid minute
(914 bpm in total over those days) and one day with minutes 100, 110, 120 give `(914 + 110) / 16 = 64.0`,
whereas the minute-weighted mean would be `(914 + 330) / 18 = 69.11`.

**Threshold (D4):** `MIN_VALID_DAYS = 14`, an absolute count of valid days (half of the default 28-day
window, constant whatever the window). A measure is NULL when its own gate count is `< 14`; exactly 14 is
available, 13 is not. Coverage counts are never gated. In a window shorter than 14 days every mean is NULL.

**Consistency with `gold_clinical_daily`** (test: reconciliation over every row): each `*_valid_days` equals the
number of the participant's daily rows with the matching non-NULL column (heart rate: `hr_valid_minute_count > 0`),
and each available mean equals the mean of the matching daily column over those days (floating tolerance).
Intended differences: (a) a measure is NULL below the threshold although daily rows exist; (b) the table
summarises the whole window with no week boundaries.

Determinism: DOUBLE values are computed with one code path and ascending date order in the full and the
incremental refresh, so equal inputs give bit-identical values.

## 7. Table lifecycle and MERGE (D9)

`refresh(con, affected)` runs inside the caller's open transaction and issues no `BEGIN`/`COMMIT`.

- The table is created if absent: `CREATE TABLE gold_chronotype_cohort (<COHORT_COLUMNS>, PRIMARY KEY
  (participant_id))`. If it exists with columns or types different from `COHORT_COLUMNS` it is dropped and
  re-created, and a rebuild forces a full recomputation: `refresh(con, affected)` then recomputes every
  enrolled participant as for `affected is None`, ignoring `affected`. `refresh` never raises for a wrong or
  missing layout.
- **`affected is None` (full path):** compute every enrolled participant from silver for the run window,
  MERGE on `participant_id` (update every non-key column when matched, insert when not), and delete every
  other key (participants no longer enrolled).
- **`affected` given (incremental path, D8):** the affected participants are the enrolled ids that appear in
  `affected` with at least one date inside the window `[study_start, study_start + study_days - 1]`; ids that
  are not enrolled, empty date sets and dates outside the window are ignored. Only the affected participants
  are recomputed (all columns) with the same function as the full path and MERGEd; every other row is not
  touched. An empty mapping changes nothing.
- A refresh on unchanged inputs MERGEs identical values: idempotent, no duplicates, row count stable.
- A raised exception propagates (INC-006 section 7 rolls the whole run back).

## 8. Incremental behavior (INC-006 integration)

- A new day, corrected record or removed file recomputes only the participants whose days changed and equals
  a full rebuild in every table (including `gold_chronotype_cohort`), `run_id` and report bytes. A corrected
  single record changes exactly one cohort row; a new day changes exactly one row; a removed file changes
  exactly the rows of the participants it fed.
- A change to the participants file (a shared input) takes the INC-006 `shared_input_changed` fallback, a full
  rebuild calling `refresh(con, None)`: every row is recomputed, including a changed chronotype, added and
  removed participants. Survey and device-metadata changes and window changes (`window_changed`) follow the same
  path and equal a full rebuild.
- A no-op incremental run changes nothing and does not call `refresh` (INC-006 section 9).
- **Old schema:** `incremental._EXPECTED_TABLES` and `_expected_schema` include `gold_chronotype_cohort` with
  `COHORT_COLUMNS` (names, types, order). A stored database without the table, or with a missing, retyped or
  reordered cohort column, falls back with `fallback_reason = "old_schema"` and equals a full rebuild.
- **Failure:** a malformed changed file or a failing refresh raises, the transaction rolls back and the previous
  output (including the cohort table) is byte-identical (INC-006 section 7).

## 9. Quality outputs (D11)

No quality rule, `quality_results` row, `quality_rejects` row, report column or `run_id` change. The cohort flag
and the coverage columns only expose the effects of existing rules and of the participants file.

## 10. Date and time semantics

Local dates only; no instant or time-zone conversion. The window is `[study_start, study_start + study_days - 1]`.
