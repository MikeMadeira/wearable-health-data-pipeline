## 1. Public contract

New module `src/wearable_pipeline/heart_rate.py` (no change to `normalize.py`):

| Name | Signature |
|------|-----------|
| `HEART_RATE_RULES` | `dict[str, tuple[str, str, str, str]]`: rule id -> (source, handling, severity, reason) (section 6) |
| `HeartRateDay` | frozen dataclass, fields in this order: `hr_mean_bpm: float \| None`, `hr_min_bpm: int \| None`, `hr_max_bpm: int \| None`, `hr_valid_minute_count: int`, `hr_quality_flags: str \| None` |
| `HeartRateLayer` | frozen dataclass of the rows built by `build_heart_rate_layer` (section 7) |
| `build_heart_rate_layer` | `build_heart_rate_layer(files: Mapping[str, Sequence[Any]], enrolled: Collection[str], window: Sequence[date]) -> HeartRateLayer` |

`run_pipeline`, `RunResult`, `PipelineError` and `main` keep their signatures. `pipeline.py` reads
the files, calls `build_heart_rate_layer`, merges `HEART_RATE_RULES` into its rule table and
writes the tables; it owns all I/O. `build_heart_rate_layer` performs no I/O and reuses
`normalize.parse_local_timestamp`. No new dependency: standard-library `json` and DuckDB.

## 2. Inputs and failure contract

Heart-rate files are the manifest rows with `source = 'heart_rate'`
(`wearable_events/<folder>/heart_rate.json`). A participant without such a file is allowed.

`PipelineError` (CLI exit 1, before any table is touched) is added for: a heart-rate file that
cannot be read or is not valid UTF-8 JSON; a file whose top level is not an array; an array
element that is not an object (same contract as sleep and steps; planner decision 12).
Anything inside a record object is a field-level defect and never raises.
`build_heart_rate_layer` itself never raises: a non-object element is treated as `{}` and its
reject carries the element as given. `files` is processed in sorted path order, so output is
independent of mapping order.

## 3. Record typing

Each record is an object with `timestamp`, `heart_rate_bpm` and optionally `participant_id`.

- `timestamp`: `parse_local_timestamp` (naive = UTC-05:00 local; `Z` or an offset is converted;
  anything else unparseable). `minute_ts` is the parsed local naive timestamp, seconds kept
  (never floored); `local_date` is its calendar date, **after conversion**. The **slot** of a
  record is `minute_ts` truncated to the minute; the slot is used only for duplicate and run
  detection.
- A record is **converted** when its timestamp parsed and its text (stripped) ends with `Z` or
  carries a `+hh:mm` / `-hh:mm` offset, even when the offset is `-05:00` or the date does not
  change (decision 6). `raw_timestamp` then holds the original text unchanged; it is NULL for
  every other record, including unparseable ones (their text is in `quality_rejects`).
- `heart_rate_bpm` (raw value): **valid** only when it is a JSON integer (not boolean, float,
  string, null, list or object) in the int32 range. Otherwise it is invalid. A valid integer
  outside 40..200 is typed but flagged `HR_VALUE_OUT_OF_RANGE`. A missing key is invalid.
- Participant id: the record's `participant_id` when it is a non-blank string, else the folder
  name in the path; used as given.
- Value precedence: invalid -> `HR_VALUE_INVALID` only; valid and outside inclusive 40..200 ->
  `HR_VALUE_OUT_OF_RANGE` only; otherwise the value is *candidate* (in range). Stuck-run and
  duplicate rules are evaluated afterwards and can still withhold a candidate.

### 3a. Normalized value

`heart_rate_bpm_normalized` equals the raw integer when the record is a candidate (valid,
inclusive 40..200) **and** not a member of a conflicting duplicate group **and** not flagged
`HR_STUCK_SENSOR_RUN`; otherwise NULL. Normalization never changes `heart_rate_bpm`.
Orphan, folder-mismatched, out-of-window, unparseable-timestamp and non-minute-aligned records
keep their normalized value when it is otherwise non-NULL; only gold ignores them.

## 4. Silver: `silver_heart_rate_minute`

Grain: one row per element of every heart-rate file, none dropped, ordered by (path, array
position). Natural key (`participant_id`, `minute_ts`), unique except for identical
timestamps (duplicates) and NULL `minute_ts`. No row-number column.

| # | Column | Type | Content |
|---|--------|------|---------|
| 0 | `participant_id` | VARCHAR | section 3 |
| 1 | `local_date` | DATE | local date after conversion; NULL when unparseable |
| 2 | `minute_ts` | TIMESTAMP | local naive timestamp; NULL when unparseable |
| 3 | `raw_timestamp` | VARCHAR | original timestamp text for converted records, else NULL |
| 4 | `heart_rate_bpm` | INTEGER | the **raw** value as typed: the integer whenever valid int32 (including out of range, stuck and duplicate members); NULL **only** when invalid |
| 5 | `heart_rate_bpm_normalized` | INTEGER | section 3a |
| 6 | `is_orphan` | BOOLEAN | participant id not enrolled |
| 7 | `is_out_of_window` | BOOLEAN | parsed timestamp whose local date is outside the window |
| 8 | `is_duplicate_minute` | BOOLEAN | the record shares its slot with another (exact or conflicting) |
| 9 | `is_out_of_range` | BOOLEAN | `HR_VALUE_OUT_OF_RANGE` raised |
| 10 | `is_stuck_sensor` | BOOLEAN | `HR_STUCK_SENSOR_RUN` raised |
| 11 | `is_timestamp_converted` | BOOLEAN | the record is converted |
| 12 | `quality_flags` | VARCHAR | comma-joined alphabetically sorted rule ids, or NULL |

13 columns. `HeartRateLayer.rows` tuples use the same order and indexes.

## 5. Duplicates, stuck runs and daily aggregates

**Duplicate groups.** Group by (participant id, slot) the records whose timestamp parsed and
that are not folder-mismatched (a mismatched record never creates or joins a group). The
signature of a member is the JSON text of its raw `heart_rate_bpm` value (or an absent
marker). One distinct signature in a group of two or more: **exact**; two or more signatures:
**conflict**. Members of a group carry the group's rule and `is_duplicate_minute`. Conflict
members have NULL normalized values (raw and flags stay); exact members keep theirs and the
slot counts once. A converted record and a naive record that land in the same slot are in the
same group.

**Stuck runs (M-04).** Per participant id, over **all** records with a parsed timestamp that
are not folder-mismatched (orphan and out-of-window records included; the timeline is not cut
at the window or at midnight), a slot is *clean* when its group has exactly one signature
and that raw value is a valid integer in 40..200. A **run** is a maximal sequence of clean
slots exactly one minute apart with the same value. A missing slot, an out-of-range or invalid
slot, a conflict slot, or a different value ends the run. An exact group is one slot. A run of
`>= 60` slots (threshold provisional) flags **every** record of **every** slot of the run,
starting with the first, with `HR_STUCK_SENSOR_RUN` and withholds their normalized values. 59
identical minutes are not flagged; 60 and 61 are. Input order is irrelevant. A run may span
midnight; each affected local day receives the flag for its minutes.

**Contribution.** A record is *in scope* when not orphan, not folder-mismatched, timestamp
parsed and local date inside the window. A slot contributes when its in-scope records have a
non-NULL normalized value (an exact group once; a conflict group never). For each (participant,
local date) with at least one in-scope record:

- `hr_mean_bpm` = sum of contributing normalized values / number of contributing slots, plain
  floating-point division, **not rounded** (decision 4); NULL when none contribute;
- `hr_min_bpm`, `hr_max_bpm` = smallest and largest contributing value; NULL when none;
- `hr_valid_minute_count` = contributing slots; 0 when none;
- `hr_quality_flags` = comma-joined sorted distinct rule ids over the day's in-scope records
  (the exclude rules cannot appear), or NULL. `HR_TIMESTAMP_CONVERTED` therefore appears on
  every day with an in-scope converted record, on the **converted** (local) date.

Days without any in-scope record have no entry. Missing minutes are not imputed, not zero and
not counted; gaps show as a lower count. Out-of-order records change nothing.

## 6. Quality rules

All rules use source `heart_rate`. `checked_count` is the number of records read (zero without
heart-rate files); `failed_count` the number of records flagged by the rule (once per record
and rule). Every rule always produces one `quality_results` row. One `quality_rejects` row is
written per flagged record and rule, `row_ref` `"{relative_path}:{array_position}"` (1-based),
`raw_values` the JSON of the raw record as given (`ensure_ascii` off) and `reason` the rule's
text, **except `HR_TIMESTAMP_CONVERTED`, which writes no rejects** (informational). The
pipeline takes heart-rate `failed_count` from `HeartRateLayer.failed`, not from rejects.

| rule_id | Record fails when | Handling | Severity | Reason (exact text) |
|---------|-------------------|----------|----------|---------------------|
| `HR_ORPHAN_PARTICIPANT` | participant id not enrolled | `exclude_from_output` | `medium` | `heart rate participant_id is not enrolled in participants.csv` |
| `HR_PARTICIPANT_FOLDER_MISMATCH` | `participant_id` is a non-blank string different from the folder | `exclude_from_output` | `medium` | `heart rate participant_id differs from its participant folder` |
| `HR_TIMESTAMP_UNPARSEABLE` | `timestamp` missing or unparseable | `exclude_from_output` | `medium` | `heart rate timestamp is missing or not a valid ISO 8601 timestamp` |
| `HR_TIMESTAMP_OUT_OF_WINDOW` | parsed local date outside the window | `exclude_from_output` | `medium` | `heart rate timestamp is outside the study window` |
| `HR_VALUE_INVALID` | `heart_rate_bpm` null, missing or not an int32 integer | `withhold_field` | `medium` | `heart_rate_bpm is missing, not an integer, or outside the 32-bit integer range` |
| `HR_VALUE_OUT_OF_RANGE` (M-03) | valid integer outside inclusive 40..200 | `withhold_field` | `high` | `heart_rate_bpm is outside the range 40 to 200` |
| `HR_STUCK_SENSOR_RUN` (M-04) | record belongs to a run of >= 60 identical minute slots | `withhold_field` | `medium` | `heart_rate_bpm repeats for at least 60 consecutive minutes` |
| `HR_TIMESTAMP_CONVERTED` (M-05) | converted record (section 3) | `convert` | `low` | `heart rate timestamp with Z or an offset converted to UTC-05:00` |
| `HR_DUPLICATE_MINUTE_CONFLICT` (M-07) | member of a conflict group | `withhold_field` | `high` | `records for one participant-minute have different values` |
| `HR_DUPLICATE_MINUTE_EXACT` (M-07) | member of an exact group | `flag` | `medium` | `records for one participant-minute have identical values` |
| `HR_TIMESTAMP_NOT_MINUTE_ALIGNED` (M-09) | parsed timestamp with non-zero seconds or microseconds | `flag` | `medium` | `heart rate timestamp is not aligned to a whole minute` |

Notes:

- 11 heart-rate rules; the rule table grows from 30 to 41 rows, listed in the report and
  `quality_results` ordered by `rule_id`, `source`. In flag strings ids sort alphabetically:
  `HR_DUPLICATE_*`, `HR_ORPHAN_*`, `HR_PARTICIPANT_*`, `HR_STUCK_*`, `HR_TIMESTAMP_*`,
  `HR_VALUE_*`.
- `HR_TIMESTAMP_CONVERTED` counts converted records (2,880 on the profiled data, 600 of them
  with a date change), is informational and has failed count above its (zero) rejects.
- Unobserved-defect rules (`HR_VALUE_INVALID`, `HR_TIMESTAMP_UNPARSEABLE`,
  `HR_TIMESTAMP_OUT_OF_WINDOW`, `HR_PARTICIPANT_FOLDER_MISMATCH`, `HR_ORPHAN_PARTICIPANT`)
  report zero on the profiled data.
- `HR_STUCK_SENSOR_RUN` failed count is the number of flagged records (360 on profiled data
  if no flagged slot is duplicated); the duplicate rules are independent of the stuck rule.
- `HR_TIMESTAMP_UNPARSEABLE` and `HR_VALUE_INVALID` both fire for `{}` (missing keys).
- Counts of the observed rules are recomputed under these definitions (human evidence step).

## 7. `HeartRateLayer`

Frozen dataclass, fields in this order: `rows` (silver tuples in (sorted path, array
position) order, section 4), `rejects` (`(rule_id, relative_path, array_position, raw_record)`
in record order, rules sorted within a record, none for `HR_TIMESTAMP_CONVERTED`), `failed`
(`Counter` rule id -> flagged records, including converted), `checked` (records read),
`daily` (`dict[tuple[str, date], HeartRateDay]`).

## 8. Gold: new columns of `gold_clinical_daily`

The existing 22 columns, key (`participant_id`, `local_date`), staged row set (enrolled ids x
window dates) and values are unchanged. Six new columns (gold 22 -> 28), appended in this order:

| Column | Type | Rule |
|--------|------|------|
| `hr_mean_bpm` | DOUBLE | `HeartRateDay.hr_mean_bpm`; NULL when none |
| `hr_min_bpm` | INTEGER | `HeartRateDay.hr_min_bpm`; NULL when none |
| `hr_max_bpm` | INTEGER | `HeartRateDay.hr_max_bpm`; NULL when none |
| `hr_valid_minute_count` | INTEGER | contributing slots, 0 when none |
| `hr_present` | BOOLEAN | true when the day has an entry in `daily` (an in-scope record, valid or not) |
| `hr_quality_flags` | VARCHAR | `HeartRateDay.hr_quality_flags` or NULL |

A day with no records holds NULL, NULL, NULL, 0, false, NULL (also for a participant without
`heart_rate.json`). A day whose in-scope records are all withheld holds NULL, NULL, NULL, 0,
true and the flags. Orphan, out-of-window, unparseable and folder-mismatched records never
contribute, even to `hr_present`.

### Table evolution and MERGE

`gold_clinical_daily` is created with 28 columns when absent. When it exists without some of
them (10-, 16- or 22-column tables, or any prior shape), each missing column is added with
`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` before the MERGE; existing rows keep values and get
NULL in added columns. Staging inserts and the MERGE address columns by name. The MERGE keeps
`ON participant_id AND local_date`: matched rows update all non-key columns, unmatched rows are
inserted, rows no longer staged are retained (with NULL heart-rate columns when old).

## 9. Operational contract

- Determinism: no time, randomness or machine paths in tables or report; a rerun on unchanged
  inputs yields identical tables and a byte-identical report; mapping order is irrelevant.
- Idempotency: reruns never duplicate a key; changing one heart-rate record changes exactly
  that participant-day's heart-rate columns and no other gold cell (a record inside a stuck
  run on two days is the only case that may legitimately change two days); survey, sleep and
  steps changes do not change heart-rate columns.
- Full rebuild; raw files unchanged; nothing created under `data_dir`; `run_id` unchanged
  (derived from the manifest, which already lists `heart_rate.json` files).
- Scale: about 2,015,000 real records. The implementation bulk-loads `silver_heart_rate_minute`
  and the heart-rate rows of `quality_rejects` as for steps (CSV `COPY`, no `executemany`). A
  test runs 60,000 records (6,000 of them `Z`) through the pipeline in under 25 s. Real-data
  run time is recorded by the human.

## 10. Examples

File `wearable_events/P001/heart_rate.json`, window starting 2026-01-08 (`m` = minutes after
00:00):

| Pos | Timestamp | bpm | Normalized | Rules |
|-----|-----------|-----|------------|-------|
| 1 | m0 | 60 | 60 | none |
| 2 | m1 | 70 | 70 | `HR_DUPLICATE_MINUTE_EXACT` (also pos 3) |
| 3 | m1 | 70 | 70 | `HR_DUPLICATE_MINUTE_EXACT` |
| 4 | m2 | 300 | NULL | `HR_VALUE_OUT_OF_RANGE` (raw 300 kept) |
| 5, 6 | m3 | 50, 51 | NULL, NULL | `HR_DUPLICATE_MINUTE_CONFLICT` each |
| 7 | `2026-01-09T04:30:00Z` | 80 | 80 | `HR_TIMESTAMP_CONVERTED`; local 2026-01-08 23:30; `raw_timestamp` kept |
| 8 | m1440 | 90 | 90 | none (2026-01-09) |

Day 2026-01-08: mean 70.0, min 60, max 80, valid minutes 3 (m0, m1, 23:30), flags
`HR_DUPLICATE_MINUTE_CONFLICT,HR_DUPLICATE_MINUTE_EXACT,HR_TIMESTAMP_CONVERTED,HR_VALUE_OUT_OF_RANGE`.
Day 2026-01-09: 90.0, 90, 90, 1, NULL. Failed: conflict 2, exact 2, converted 1, out of range
1; 5 rejects. 41 `quality_results` rows.

Stuck runs: 59 identical minutes -> no flag; 60 and 61 -> every minute flagged; a 60-minute run
from 23:30 to 00:29 flags 30 minutes on each of two days.
