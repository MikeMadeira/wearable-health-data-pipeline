# INC-007: Weekly Biostatistics Table (`gold_biostat_weekly`)

Status: Approved (decisions D1-D11 in section 12 ratified by the human at G2 on 2026-10-14)
Source intent: `intents/INC-007-weekly-biostatistics.md`
Upstream decisions: `reports/INC-001/profiling-findings.md` Section 7, items 6 and 7 (study-relative
seven-day blocks anchored on 2026-01-08; a distinct wide participant-week table with period
boundaries, approved measures and valid-day/coverage fields) and the field-level decisions (no
imputation; missing steps are not zero and missing heart rate is not a measured value; exact
duplicate minutes do not inflate counts; conflicting duplicates are omitted from aggregates;
coverage and valid counts are exposed).
Amends: `specs/INC-006.md` section 9 (`DERIVED_TABLES` is no longer empty: it holds the weekly
table) and section 5 (the old-schema check also covers `gold_biostat_weekly`). Everything not
named here is unchanged: `run_pipeline`, `run_incremental`, `compare_outputs`, the CLI, every existing
table's columns and values (including `gold_clinical_daily`), `run_id`, `quality_results`,
`quality_rejects` and the report.

## 1. Public contract

New module `src/wearable_pipeline/weekly.py`:

| Name | Shape |
|------|-------|
| `TABLE_NAME` | `"gold_biostat_weekly"` |
| `WEEK_LENGTH_DAYS` | `7` |
| `MIN_VALID_DAYS` | `4` (section 6) |
| `WEEKLY_COLUMNS` | ordered tuple of `(name, duckdb_type)`, section 3 |
| `week_count(study_days: int) -> int` | pure; number of whole seven-day weeks: `study_days // 7`, never negative |
| `week_bounds(study_start: date, week_id: int) -> tuple[date, date]` | pure; `(study_start + 7*(week_id-1), that + 6 days)`; `ValueError` if `week_id < 1` |
| `week_of(study_start: date, study_days: int, day: date) -> int \| None` | pure; the `week_id` of `day`, or `None` when `day` is before `study_start` or lies outside the whole weeks of the window |
| `WeeklyBiostat` | class implementing `incremental.DerivedTable`; `name == TABLE_NAME`; `refresh(con, affected) -> None` |
| `WEEKLY` | the single `WeeklyBiostat()` instance registered in `incremental.DERIVED_TABLES` |

`incremental.DERIVED_TABLES` is `[WEEKLY]` (read at call time as today). `weekly` must not import
`incremental` (no cycle: `incremental` imports `weekly`). No new runtime dependency (standard
library and DuckDB). No CLI change: `run` and `compare` already cover any table by name discovery.

## 2. Grain, key and week definition

- **Output grain:** one row per enrolled participant and whole study week. Key
  (`participant_id`, `week_id`), declared `PRIMARY KEY` and used for the MERGE.
- **Enrolled participants:** the distinct `participant_id` values of `silver_participants` (a
  participant listed twice in `participants.csv` yields one set of rows). Participants that are not
  enrolled (orphans) never get a row.
- **Window:** read from the `run_window` table (`study_start`, `study_days`) of the same database,
  written by every run before derived tables refresh. The weekly table never infers the window from
  gold dates.
- **Weeks:** week `w` (1-based) covers the seven local dates
  `study_start + 7(w-1)` ... `study_start + 7(w-1) + 6`; `period_start_date` and `period_end_date`
  are those first and last dates (inclusive). Default window (start 2026-01-08, 28 days):
  week 1 = 2026-01-08..14, 2 = 01-15..21, 3 = 01-22..28, 4 = 01-29..02-04.
- **`week_id`:** INTEGER, the study-relative week number 1, 2, 3, 4 (decision D1).
- **Window not a multiple of seven:** only whole weeks are emitted, `week_count(study_days) =
  study_days // 7`. The trailing partial block (study_days mod 7 days) produces no row, and its days
  contribute to no weekly value. `study_days < 7` gives an existing, empty table. Examples:
  28 -> 4 weeks, 27 -> 3 (days 22-26 dropped), 10 -> 1, 6 -> 0.
- **Cardinality:** `enrolled participants x week_count(study_days)` rows. Default window with 50
  enrolled participants: 200 rows. Every enrolled participant-week has a row even with no data at all
  (all coverage counts 0, all measures NULL).
- **Local dates** are the `local_date` values of the silver tables (INC-003 to INC-005 day
  assignment); no time-zone logic is added.

## 3. Schema

All columns are listed in this order. The table shares **only** `participant_id` with
`gold_clinical_daily`; it has no `local_date` and no daily column name (test:
`set(weekly names) & set(daily names) == {"participant_id"}`).

| # | Column | Type | Meaning |
|---|--------|------|---------|
| 1 | `participant_id` | VARCHAR | key |
| 2 | `week_id` | INTEGER | key, 1-based |
| 3 | `period_start_date` | DATE | first day of the week |
| 4 | `period_end_date` | DATE | last day of the week (start + 6) |
| 5 | `valid_days` | INTEGER | days of the week with at least one valid wearable value: `sleep_valid` or `steps_valid` or `hr_valid` (section 4); 0..7; the survey does not count |
| 6 | `sleep_valid_days` | INTEGER | days with a non-NULL daily total sleep minutes |
| 7 | `sleep_stage_valid_days` | INTEGER | days with a non-NULL daily deep-sleep share (equally: efficiency) |
| 8 | `steps_valid_days` | INTEGER | days with a non-NULL daily total steps |
| 9 | `steps_valid_minutes` | BIGINT | sum over the week of the daily valid step-minute counts |
| 10 | `hr_valid_days` | INTEGER | days with at least one valid heart-rate minute |
| 11 | `hr_valid_minutes` | BIGINT | sum over the week of the daily valid heart-rate minute counts |
| 12 | `fatigue_valid_days` | INTEGER | days with a non-NULL daily fatigue score |
| 13 | `stress_valid_days` | INTEGER | same for stress |
| 14 | `readiness_valid_days` | INTEGER | same for readiness |
| 15 | `sleep_quality_valid_days` | INTEGER | same for sleep quality |
| 16 | `sleep_total_min_mean` | DOUBLE | mean nightly sleep minutes |
| 17 | `deep_sleep_pct_mean` | DOUBLE | mean of daily deep-sleep share |
| 18 | `sleep_efficiency_pct_mean` | DOUBLE | mean of daily stage-derived efficiency |
| 19 | `steps_total` | BIGINT | sum of daily total steps over valid days |
| 20 | `steps_daily_mean` | DOUBLE | mean of daily total steps over valid days |
| 21 | `steps_rest_to_moderate_minutes` | BIGINT | sum of daily at-rest-to-moderate minutes |
| 22 | `steps_burst_minutes` | BIGINT | sum of daily burst minutes |
| 23 | `hr_weekly_mean_bpm` | DOUBLE | mean over all valid heart-rate minutes of the week (minute-weighted) |
| 24 | `hr_weekly_min_bpm` | INTEGER | lowest valid minute of the week |
| 25 | `hr_weekly_max_bpm` | INTEGER | highest valid minute of the week |
| 26 | `fatigue_score_mean` | DOUBLE | mean of daily fatigue scores |
| 27 | `stress_score_mean` | DOUBLE | mean of daily stress scores |

| 29 | `sleep_quality_score_mean` | DOUBLE | mean of daily sleep-quality scores |

Columns 1-15 are NOT NULL (coverage columns are never NULL: `0` means no valid data). Columns 16-29
are NULL when their aggregate is unavailable (section 6). The weekly table never stores 0 for "no
data".

## 4. Source and per-day values (silver, not gold)

`WeeklyBiostat.refresh` reads **only** the silver tables (`silver_participants`,
`silver_wellness_survey`, `silver_sleep_sessions`, `silver_sleep_stages`, `silver_steps_minute`,
`silver_heart_rate_minute`) and `run_window`. It never reads `gold_clinical_daily` (test: altering
gold values then running `refresh(con, None)` leaves the weekly rows unchanged). It re-derives, per
participant and local date, exactly the values the daily builders put in `gold_clinical_daily`, so
the "same silver values, quality flags and withheld-value rules" hold by construction:

- **Day scope:** a silver row contributes to a day only when the daily builder lets it contribute:
  not orphan, `local_date` not NULL, not out of window, and (steps and heart rate) its
  `quality_flags` do not contain the folder-mismatch rule (`STEPS_PARTICIPANT_FOLDER_MISMATCH`,
  `HR_PARTICIPANT_FOLDER_MISMATCH`).
- **Sleep day** (`specs/INC-003.md`): one value set per participant-date from
  `silver_sleep_sessions` and `silver_sleep_stages`, using `compute_sleep_metrics` on the stage
  pairs of each session; the date's value set is the **set of distinct session metrics**: exactly one
  distinct metric set (including two or more sessions with identical metrics) gives that one value
  set, never a sum or a pooled computation (two identical 400-minute sessions give 400, not 800);
  two or more distinct metric sets withhold all three values (the daily rule). The three values
  are `total_sleep_min`, `deep_sleep_pct`, `sleep_efficiency_pct`.
  - **Attributing stages to sessions (decision D10).** `silver_sleep_stages` has no session id, only
    (`participant_id`, `local_date`, `stage_index`, ...). The daily builder writes the stages of each
    session consecutively in session order with `stage_index` restarting at 1 for every session.
    The weekly refresh attributes stages to sessions the same way: for one participant-date, a new
    session starts at each stage row with `stage_index = 1` (silver insertion order, `rowid`), and the
    session's pairs are `(stage, duration_min or NULL when the stage has an unparseable time)` exactly
    as the daily builder builds them. Any other method is allowed only if it reproduces the daily
    value for every case (the reconciliation tests decide). Sessions are counted from
    `silver_sleep_sessions` (not orphan, `local_date` not NULL, not out of window); a session that
    has no stage rows contributes the all-NULL metric set (as the daily builder does, so it
    conflicts with any session that has metrics). A session whose `sleep_onset`/`sleep_end` is
    unparseable still contributes its stages' metrics (flags never remove a session). Stages of
    orphan, undated or out-of-window sessions never contribute.
- **Steps day** (`specs/INC-004.md`): per minute slot (timestamp floored to the minute) one
  `steps_per_minute`; an exact duplicate slot counts once; a conflicting duplicate slot counts as
  missing (silver already stores NULL). Day values: total, valid-minute count, at-rest-to-moderate
  and burst minute counts, over slots with a non-NULL value.
- **Heart-rate day** (`specs/INC-005.md`): per slot one `heart_rate_bpm_normalized`; withheld
  slots (out of range, invalid, stuck run, conflicting duplicate) are missing; exact duplicates
  count once. Day values: sum and count of valid minutes (mean, min, max follow).
- **Survey day** (`specs/INC-002.md`): per score the distinct non-NULL value over the
  contributing rows of the date; NULL when absent, invalid, or the rows disagree.

A day is **valid** for a source when its daily count/value is non-NULL as in the table of
section 3 (sleep: `total_sleep_min`; steps: `total_steps`; heart rate: at least one valid minute;
each survey score: that score). A flagged day whose values survive the withheld-value rules is valid
(flags do not invalidate a day; the daily rules already withheld what is unusable).

Implementations should reuse the existing builder helpers (for example `compute_sleep_metrics`)
rather than re-implement their logic, so that weekly and daily values cannot drift.

## 5. Weekly statistics

For one participant-week, over the days of that week only (never imputed, missing days and minutes
are simply absent):

| Measure | Statistic (over valid days / minutes of that measure) | Gate (section 6) |
|---------|--------------------------------------------------------|------------------|
| `sleep_total_min_mean` | mean of daily `total_sleep_min` | `sleep_valid_days` |
| `deep_sleep_pct_mean`, `sleep_efficiency_pct_mean` | mean of the daily values | `sleep_stage_valid_days` |
| `steps_total` | sum of daily `total_steps` | `steps_valid_days` |
| `steps_daily_mean` | `steps_total / steps_valid_days` | `steps_valid_days` |
| `steps_rest_to_moderate_minutes`, `steps_burst_minutes` | sum of the daily minute counts | `steps_valid_days` |
| `hr_weekly_mean_bpm` | sum of valid minute values / `hr_valid_minutes` (equivalently the daily means weighted by daily valid-minute counts) | `hr_valid_days` |
| `hr_weekly_min_bpm`, `hr_weekly_max_bpm` | minimum / maximum valid minute of the week (= min of daily mins / max of daily maxes) | `hr_valid_days` |
| `fatigue_score_mean` ... `sleep_quality_score_mean` | mean of that score's daily values | that score's `*_valid_days` |

Consistency with `gold_clinical_daily` (test: reconciliation over every row): for every available
aggregate, `steps_total == sum(total_steps)` of the week's daily rows, the means equal the means of the
daily columns over their non-NULL days, `hr_weekly_mean_bpm * hr_valid_minutes == sum(hr_mean_bpm *
hr_valid_minute_count)` (within floating tolerance), min/max equal the min of `hr_min_bpm` / max of
`hr_max_bpm`, minute counts equal the sums of the daily counts. **Intended differences from a naive
reading:** (a) the weekly heart-rate mean is weighted by valid minutes, not the mean of daily means;
(b) a measure is NULL below the coverage threshold even though daily rows exist; (c) a missing day
is never a zero day (`steps_total` is a sum over valid days only, `steps_valid_days` shows how many).

Determinism: DOUBLE values are computed with the same code path and a fixed ordering (days
ascending) in the full and the incremental refresh, so equal inputs give bit-identical values.

## 6. Coverage and minimum-coverage threshold

- Coverage columns 5-15 are always populated (section 3) and expose partial weeks.
- **Threshold (decision D2):** `MIN_VALID_DAYS = 4`. A measure is NULL when its own valid-day count
  (the gate column in section 5) is `< 4`, i.e. a weekly aggregate is available only when at least
  four of the seven days carry valid data for that measure. Exactly 4 is available; 3 is not.
  Coverage counts themselves are never gated.
- A source with no data in a week gives `0` coverage and NULL measures (missing is not a value).

## 7. Table lifecycle and MERGE

`refresh(con, affected)` runs inside the caller's open transaction and issues no `BEGIN`/`COMMIT`.

- The table is created if absent: `CREATE TABLE gold_biostat_weekly (<WEEKLY_COLUMNS>, PRIMARY KEY
  (participant_id, week_id))`. If it exists with columns or types different from `WEEKLY_COLUMNS`
  it is dropped and re-created (rebuild). **A rebuild forces a full recomputation (decision D11):**
  when the table was absent or had a different layout, `refresh(con, affected)` recreates it and
  recomputes and inserts every enrolled participant-week exactly as for `affected is None`,
  ignoring `affected` (a partial table is never left behind). Through `run_incremental` this is
  unreachable (the old-schema check falls back first); it governs only a direct call. `refresh` never
  raises for a wrong or missing layout.
- **`affected is None` (full rebuild path):** compute every enrolled participant-week from silver
  for the run window, MERGE on (`participant_id`, `week_id`) (update every non-key column when
  matched, insert when not), and delete every other key (participants no longer enrolled, weeks
  beyond a shrunken window). Called by `run_pipeline` and by every fallback, shared-input and
  window-change rebuild (INC-006 sections 5 and 9).
- **`affected` given (incremental path):** `affected` maps `participant_id` to the local dates
  whose `gold_clinical_daily` row was recomputed. The affected participant-weeks are
  `{(pid, week_of(start, days, day))}`; a date whose `week_of` is `None` (trailing partial block)
  and a participant that is not enrolled are ignored. Only those participant-weeks are recomputed
  (all columns) and MERGEd; every other row is not touched. The recomputation uses the same
  function as the full path. An empty mapping changes nothing.
- A refresh on unchanged inputs MERGEs identical values: idempotent, no duplicates, row count stable.
- A raised exception propagates (INC-006 section 7 rolls the whole run back).

## 8. Incremental behavior (INC-006 integration)

- `run_incremental` after a new day, a corrected record or a removed file recomputes only the
  participant-weeks containing an affected day and equals a full rebuild in every table (including
  `gold_biostat_weekly`), `run_id` and report bytes.
- A corrected single record changes exactly one weekly row (the participant-week containing its
  day); a removed file changes exactly the participant-weeks of the days it fed; a new day changes
  exactly one participant-week.
- A no-op incremental run changes nothing and does not call `refresh` (INC-006 section 9).
- **Shared input** (participants, survey, device metadata) or **window** change: the INC-006
  fallback (`shared_input_changed`, `window_changed`) runs a full rebuild, which calls
  `refresh(con, None)`; the weekly table, including rows deleted for removed participants or
  shrunken windows, equals a full rebuild.
- **Old schema:** `incremental._EXPECTED_TABLES`/`_expected_schema` include `gold_biostat_weekly`
  with `WEEKLY_COLUMNS` (names, types, order). A stored database without the table or with a
  missing, retyped or reordered weekly column falls back with `fallback_reason = "old_schema"` and
  the result equals a full rebuild.
- **Failure:** a malformed changed file or a failing refresh raises, the transaction rolls back and
  the previous output (including the weekly table) is byte-identical, as in INC-006 section 7.

## 9. Quality outputs

No quality rule, `quality_results` row, `quality_rejects` row, report column or `run_id` change.
The weekly coverage columns only expose the effects of the existing daily rules. (Decision D5: no
new rule is needed.)

## 10. Date and time semantics

Weeks are local-date blocks. There is no instant or time-zone conversion in the weekly table. The
period dates are plain DATEs, inclusive at both ends.

## 13. Worked example

Window 14 days from 2026-01-08. P001 has valid heart-rate minutes 60, 70 (01-08), 80 (01-09), 90, 100,
110 (01-10; the 90 recorded twice, counted once) and 50 (01-11), plus an out-of-range 300 on 01-09
(withheld). Week 1: `hr_valid_days = 4`, `hr_valid_minutes = 7`, `hr_weekly_mean_bpm = 560 / 7 = 80.0`
(the mean of daily means would be 73.75), `hr_weekly_min_bpm = 50`, `hr_weekly_max_bpm = 110`. In week 2
P001 has valid heart rate on only 3 days: `hr_valid_days = 3`, `hr_valid_minutes = 3`, and the three
heart-rate measures are NULL. P002 with no heart-rate data has `hr_valid_days = 0`,
`hr_valid_minutes = 0` and NULL heart-rate measures, never 0.
