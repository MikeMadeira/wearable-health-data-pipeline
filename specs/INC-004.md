## 1. Public contract

New module `src/wearable_pipeline/steps.py` (no change to `normalize.py`):

| Name | Signature |
|------|-----------|
| `STEPS_RULES` | `dict[str, tuple[str, str, str, str]]`: rule id -> (source, handling, severity, reason) (section 6) |
| `StepsDay` | frozen dataclass, fields in this order: `total_steps: int \| None`, `steps_valid_minute_count: int`, `minutes_rest_to_moderate: int`, `minutes_burst: int`, `steps_quality_flags: str \| None` |
| `StepsLayer` | frozen dataclass of the rows built by `build_steps_layer` (section 7) |
| `build_steps_layer` | `build_steps_layer(files: Mapping[str, Sequence[Any]], enrolled: Collection[str], window: Sequence[date]) -> StepsLayer` |

`run_pipeline`, `RunResult`, `PipelineError` and `main` keep their signatures. `pipeline.py`
reads the files, calls `build_steps_layer`, merges `STEPS_RULES` into its rule table and
writes the tables; it owns all I/O. `build_steps_layer` performs no I/O and reuses
`normalize.parse_local_timestamp`. No new dependency: standard-library `json` and DuckDB.

## 2. Inputs and failure contract

Steps files are the manifest rows with `source = 'steps'`
(`wearable_events/<folder>/steps.json`). A participant without a steps file is allowed.

`PipelineError` (CLI exit 1, before any table is touched) is added for: a steps file that
cannot be read or is not valid UTF-8 JSON; a steps file whose top level is not an array; an
array element that is not an object. All earlier failure conditions are unchanged. Anything
inside a record object (missing keys, wrong types, bad values) is a field-level defect and
never raises. `build_steps_layer` itself never raises: it treats a non-object element as an
empty object `{}` (its reject carries the element as given).

`files` maps relative path to the parsed JSON array, in any order; the layer sorts paths, so
output is independent of mapping order.

## 3. Record typing and conversion

Each record is an object with `timestamp`, `steps` and optionally `participant_id` and the
undocumented `_unit`. Missing keys are treated as invalid values of the field.

- `timestamp`: `parse_local_timestamp` (naive = UTC-05:00 local; `Z` or an offset is
  converted; non-strings and any other layout are unparseable). `minute_ts` is the parsed
  local naive timestamp unchanged (seconds are kept, never floored) and `local_date` its
  calendar date. The **slot** of a record is `minute_ts` truncated to the minute (seconds and
  microseconds set to 0); the slot is used only for duplicate detection.
- `steps` (raw value): valid when it is a JSON integer (not a boolean, float, string or null)
  between -2147483648 and 2147483647. Otherwise it is invalid. A valid negative integer is valid
  typing but is flagged `STEPS_NEGATIVE`.
- `_unit`: present when the key exists (any value, including `null`). The `unit` column holds
  the value when it is a string, else the JSON text of the value (for example `null`, `5`,
  `true`, `3.5`); it is NULL when the key is absent. The unit text is never altered by
  conversion.
- Participant id: the record's `participant_id` when it is a non-blank string, else the name
  of the participant folder in the path. The record id is used as given (no trimming).

### 3a. Normalized per-minute value and rule precedence

Each record gets a **normalized per-minute value** (`steps_per_minute`), decided per record from
its own `steps` and `_unit`; the unit is never assumed from the participant or from other
records. Evaluate in this order; the first matching case applies and rules from later cases
are not evaluated for that record:

1. `steps` invalid: `STEPS_VALUE_INVALID`; normalized value NULL.
2. `steps` a valid integer below 0 (whatever the unit, including an unrecognized one):
   `STEPS_NEGATIVE`; normalized value NULL; never converted and never `STEPS_UNIT_*`.
3. `steps` a valid integer >= 0 and no `_unit` key: normalized value = `steps`; no rule.
4. `steps` a valid integer >= 0 and `_unit` present:
   - `_unit` is the string `steps_per_hour` (exact, case-sensitive) and `steps % 60 == 0`:
     converted; normalized value = `steps // 60`; `STEPS_UNIT_CONVERTED`. Zero converts to 0.
   - anything else (any other string, `null`, a number or a boolean; or an hourly value not
     divisible by 60): `STEPS_UNIT_UNSUPPORTED`; normalized value NULL.

So the convert flag appears only on records that were converted (case 4, first branch); it is
never present on an unit-less, unsupported, negative or invalid record. The other rules
(participant, timestamp, duplicate) are independent of these four cases.

**Duplicate conflicts withhold the normalized value afterwards (section 5)** but do not remove
the per-record flag: a converted record that belongs to a conflict group keeps
`STEPS_UNIT_CONVERTED` (it was converted; its slot is then withheld) and has a NULL
normalized value.

## 4. Silver: `silver_steps_minute`

Grain: one row per element of every steps file, none dropped, ordered by (path, array
position) when written. Natural key (`participant_id`, `minute_ts`), unique except where two
records share an identical timestamp (an exact or conflicting duplicate) or `minute_ts` is
NULL. Original text is recoverable from the raw files and, for rejected records, from
`quality_rejects`. No raw-text or row-number column is stored.

| Column | Type | Content |
|--------|------|---------|
| `participant_id` | VARCHAR | section 3 |
| `local_date` | DATE | local date of `minute_ts`; NULL when the timestamp is unparseable |
| `minute_ts` | TIMESTAMP | local naive timestamp; NULL when unparseable |
| `steps` | INTEGER | the **raw** value as typed: the integer whenever it is a valid int32 (including a negative value, a value with `_unit`, and a member of a conflicting duplicate group); NULL only when the value is invalid. Never altered by conversion or withholding |
| `steps_per_minute` | INTEGER | the normalized per-minute value (section 3a); NULL when invalid, negative, unsupported unit, hourly value not divisible by 60, or the record belongs to a conflicting duplicate group |
| `activity_level` | VARCHAR | derived from `steps_per_minute` (section 4a); NULL when it is NULL |
| `unit` | VARCHAR | section 3 |
| `is_orphan` | BOOLEAN | participant id not enrolled |
| `is_out_of_window` | BOOLEAN | true only for a parsed timestamp whose local date is outside the window |
| `is_duplicate_minute` | BOOLEAN | the record shares its slot with another record (exact or conflicting) |
| `quality_flags` | VARCHAR | comma-joined, alphabetically sorted rule ids that flagged the record, or NULL |

Silver has 11 columns. `steps_per_minute` is the fifth column, directly after the raw
`steps`; `activity_level` is the sixth. Row tuples of `StepsLayer.rows` use the same order:
index 0 `participant_id`, 1 `local_date`, 2 `minute_ts`, 3 `steps`, 4 `steps_per_minute`, 5
`activity_level`, 6 `unit`, 7 `is_orphan`, 8 `is_out_of_window`, 9 `is_duplicate_minute`, 10
`quality_flags`.

Orphan, folder-mismatch, out-of-window and unparseable-timestamp records have silver rows
and never reach gold; they keep their `steps_per_minute` and level whenever the value is valid
(the participant, window and timestamp rules do not withhold the value).

### 4a. Activity level

`activity_level` is computed per record from `steps_per_minute` (after conversion and after
withholding):

| `steps_per_minute` | `activity_level` |
|--------------------|------------------|
| 0 to 30 | `at_rest_to_moderate` |
| above 30 (no upper cutoff) | `burst` |
| NULL | NULL |

Boundaries: 0, 1, 29, 30 -> `at_rest_to_moderate`; 31, 32 -> `burst`. A converted value uses
the converted number: hourly 1800 -> 30 -> `at_rest_to_moderate`; 1860 -> 31 and 3600 -> 60 ->
`burst`. The record keeps its level when its normalized value is non-NULL, whatever the other
flags (exact duplicate members, orphan, folder-mismatched, out-of-window,
non-minute-aligned). The level is not a quality rule: a `burst` raises no flag, reject or
`quality_results` row. The boundary 30 comes from the data dictionary (0 to 30 steps per minute
is the expected rate at rest through moderate activity, bursts above it); no finer boundary is
defined or invented.

## 5. Duplicates, withholding and daily totals

**Duplicate groups.** Records are grouped by (participant id, slot) over the records whose
timestamp parsed and that are not folder-mismatched (a mismatched record never creates or
joins a group). A group of two or more records is a duplicate group. Group members are compared
**per record**, never assuming a unit from the participant. Each member has a signature:

- when its normalized value is non-NULL (cases 3 and 4, converted): (`value`, normalized value,
  JSON text of its `_unit` or an absent marker);
- otherwise (invalid, negative or unsupported): (`raw`, JSON text of its raw `steps` value or a
  missing marker, JSON text of its `_unit` or an absent marker). These stay distinct from every
  value signature and compare equal only to an identical raw value and unit.

Timestamps and seconds do not enter the signature. The unit text is part of the signature, so
an hourly record and a unit-less record with the same normalized value (hourly 300 and
unit-less 5) are **not** exact duplicates: they are a conflict. Two hourly records are exact
duplicates only when they have the same raw value; since conversion is injective on multiples
of 60, equal normalized value with the same unit text means equal raw value. One distinct
signature is an **exact** group, two or more are a **conflict** group. All members of a group
carry the group's rule and `is_duplicate_minute` true. The group is evaluated before any
withholding. Members of a conflict group have a NULL `steps_per_minute` and level (their raw
`steps` and `unit` stay); members of an exact group keep their normalized value.

**P005 pattern (decision).** Under per-record semantics, three unit-less records at non-zero
seconds that share their minute with hourly records are conflicts: for example hourly 240 (4
per minute) and unit-less 240 (240 per minute) in the same minute differ in both normalized
value and unit text. Each such slot is withheld (3 slots in the real data); the hourly member
still carries `STEPS_UNIT_CONVERTED` and the unit-less member
`STEPS_TIMESTAMP_NOT_MINUTE_ALIGNED`, both also `STEPS_DUPLICATE_MINUTE_CONFLICT`.

**Contribution.** A record is *in scope* when it is not an orphan, not folder-mismatched, its
timestamp parsed and its local date is in the window. A slot *contributes* when its in-scope
records have a non-NULL `steps_per_minute`. An exact group contributes one value (counted
once). A conflict group contributes nothing.

For each (participant, local date) with at least one in-scope record:

- `total_steps` = sum of the contributing slots' normalized values, NULL when no slot
  contributes (not 0);
- `steps_valid_minute_count` = number of contributing slots;
- `minutes_rest_to_moderate`, `minutes_burst` = number of contributing slots whose value has
  `activity_level` `at_rest_to_moderate`, `burst` (an exact group counts once, by its single
  value); 0 when none; always `minutes_rest_to_moderate + minutes_burst =
  steps_valid_minute_count`;
- `steps_quality_flags` = comma-joined sorted distinct rule ids over the day's in-scope
  records (the exclude rules cannot appear), or NULL. `STEPS_UNIT_CONVERTED` therefore appears
  on every day that has an in-scope converted record.

Days without any in-scope record have no entry. Missing minutes are not imputed, are not 0
and are not counted. Out-of-order records are not a defect and change nothing.

## 6. Quality rules

All rules use source `steps`. For every rule `checked_count` is the number of records read
(zero without steps files) and `failed_count` is the number of records flagged by the rule (a
record counts once per rule). Every rule always produces one `quality_results` row. One
`quality_rejects` row is written per flagged record and rule, with `row_ref`
`"{relative_path}:{array_position}"` (1-based), `raw_values` the JSON of the raw record as
given (all keys, nothing altered, `ensure_ascii` off) and `reason` the rule's reason text,
**except `STEPS_UNIT_CONVERTED`, which writes no reject rows**. Rules are independent unless
stated (precedence of the value rules: section 3a).

| rule_id | Record fails when | Handling | Severity | Reason (exact text) |
|---------|-------------------|----------|----------|---------------------|
| `STEPS_ORPHAN_PARTICIPANT` | participant id not enrolled in `participants.csv` | `exclude_from_output` | `medium` | `steps participant_id is not enrolled in participants.csv` |
| `STEPS_PARTICIPANT_FOLDER_MISMATCH` | `participant_id` is a non-blank string different from the folder name (a missing, blank or non-string id is not a mismatch) | `exclude_from_output` | `medium` | `steps participant_id differs from its participant folder` |
| `STEPS_TIMESTAMP_UNPARSEABLE` | `timestamp` is missing or `parse_local_timestamp` returns `None` | `exclude_from_output` | `medium` | `steps timestamp is missing or not a valid ISO 8601 timestamp` |
| `STEPS_TIMESTAMP_OUT_OF_WINDOW` | timestamp parses and its local date is outside the study window | `exclude_from_output` | `medium` | `steps timestamp is outside the study window` |
| `STEPS_VALUE_INVALID` | `steps` invalid (section 3) | `withhold_field` | `medium` | `steps is missing, not an integer, or outside the 32-bit integer range` |
| `STEPS_NEGATIVE` (M-02) | `steps` is a valid integer below 0, with or without `_unit` | `withhold_field` | `high` | `steps is negative` |
| `STEPS_UNIT_CONVERTED` (M-01) | case 4 converted: `_unit` is `steps_per_hour` and `steps` is a non-negative integer divisible by 60 | `convert` | `low` | `steps_per_hour value converted to steps per minute` |
| `STEPS_UNIT_UNSUPPORTED` (M-01) | case 4 not converted: `_unit` present with any other value, or an hourly value not divisible by 60 | `withhold_field` | `high` | `steps _unit is not steps_per_hour or the hourly value is not divisible by 60` |
| `STEPS_DUPLICATE_MINUTE_CONFLICT` (M-07) | the record belongs to a conflict group | `withhold_field` | `high` | `records for one participant-minute have different values` |
| `STEPS_DUPLICATE_MINUTE_EXACT` (M-07) | the record belongs to an exact group | `flag` | `medium` | `records for one participant-minute have identical values` |
| `STEPS_TIMESTAMP_NOT_MINUTE_ALIGNED` (M-09) | timestamp parses and has non-zero seconds or microseconds | `flag` | `medium` | `steps timestamp is not aligned to a whole minute` |

Notes:

- `convert` is a new handling value and `low` a new severity value in `quality_results`; the
  columns and table shape are unchanged. `STEPS_UNIT_CONVERTED` is informational: it sets the
  record flag in silver and the day's `steps_quality_flags`, and its `failed_count` is the
  number of converted records (120,963 on the profiled data), but it has no rows in
  `quality_rejects`. Therefore `quality_results.failed_count` can exceed the number of
  `quality_rejects` rows of a rule; this is intended for this rule only.
- **Pipeline requirement for failed counts.** The pipeline must take steps `failed_count`
  from `StepsLayer.failed` (as sleep does), not by counting `quality_rejects` rows, which is how
  survey counts are derived. `StepsLayer.failed[STEPS_UNIT_CONVERTED]` counts converted records
  while `StepsLayer.rejects` has no entry for them.
- There is no rule for `steps_per_minute` above 30: a burst is not a defect, never flagged,
  rejected or counted, stays in the total and gets level `burst` (section 4a). A day with only
  bursts has NULL `steps_quality_flags`.
- Quality flags are decided per record from its own raw values, except the two duplicate
  rules, which depend on the group.
- The rule table grows from 19 to 30 rows (11 steps rules); the report table and
  `quality_results` list all of them ordered by `rule_id`, `source`. In flag strings the ids
  sort alphabetically: `STEPS_DUPLICATE_*`, `STEPS_NEGATIVE`, `STEPS_ORPHAN_*`,
  `STEPS_PARTICIPANT_*`, `STEPS_TIMESTAMP_*`, `STEPS_UNIT_CONVERTED`, `STEPS_UNIT_UNSUPPORTED`,
  `STEPS_VALUE_INVALID`. A raw `.000` fraction or a `Z` suffix on a whole-minute time is
  aligned.
- `STEPS_UNIT_FIELD_PRESENT` (revision 2) no longer exists.

## 7. `StepsLayer`

Frozen dataclass with these fields, in deterministic order: `rows` (rows of
`silver_steps_minute`, one tuple per record in (sorted path, array position) order, columns
as in section 4), `rejects` (`(rule_id, relative_path, array_position, raw_record)` in record
order, rules sorted within a record; no entry for `STEPS_UNIT_CONVERTED`), `failed` (`Counter`
rule id -> flagged records, including converted ones), `checked` (number of records), and
`daily` (`dict[tuple[str, date], StepsDay]`, section 5).

## 8. Gold: new columns of `gold_clinical_daily`

The existing 16 columns, key (`participant_id`, `local_date`), staged row set (enrolled ids x
window dates) and values are unchanged. New columns (6, gold goes from 16 to 22), appended in
this order:

| Column | Type | Rule |
|--------|------|------|
| `total_steps` | BIGINT | `StepsDay.total_steps`; NULL when absent or no valid minute |
| `steps_valid_minute_count` | INTEGER | contributing minutes, 0 when none |
| `minutes_rest_to_moderate` | INTEGER | contributing minutes with level `at_rest_to_moderate`, 0 when none |
| `minutes_burst` | INTEGER | contributing minutes with level `burst`, 0 when none |
| `steps_present` | BOOLEAN | true when the day has an entry in `daily` (an in-scope record, valid or not) |
| `steps_quality_flags` | VARCHAR | `StepsDay.steps_quality_flags`, or NULL |

The two minute counts always sum to `steps_valid_minute_count`. A day without in-scope
records holds NULL, 0, 0, 0, false, NULL. A day whose in-scope records are all withheld holds
NULL, 0, 0, 0, true and the flags. Grain unchanged: one row per `participant_id` and
`local_date`.

### Table evolution and MERGE

`gold_clinical_daily` is created with all 22 columns when absent. When it exists without some
of the steps columns (a database written by INC-002 to INC-003 with 10 or 16 columns, or by
the superseded 20-column INC-004 plan that lacked the two minute columns), each missing column
is added with `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` before the MERGE (a 10-column table
also lacks the 6 sleep columns, added as in INC-003, plus the 6 steps columns; a 16-column
table gets the 6 steps columns; a 20-column table gets `minutes_rest_to_moderate` and
`minutes_burst`); existing rows keep their values and have NULL in the added columns. Because
added columns land after the existing ones, the staging inserts and the MERGE must address
columns by name, never by position (a 20-column table ends with its minute columns after
`steps_quality_flags`, a different order from a fresh table). The MERGE keeps
`ON participant_id AND local_date`: matched rows update all non-key columns, unmatched rows
are inserted, rows no longer staged are retained.

A table with the columns of the superseded revision 2 (`minutes_at_rest`, `minutes_moderate`)
is **not** supported or migrated: that plan was never released and those columns are not
dropped or maintained.

## 9. Operational contract

- Determinism: no time, randomness or machine paths in any table or the report; a rerun on
  unchanged inputs yields identical tables (compared ordered by all columns) and a
  byte-identical report; output does not depend on `files` mapping order or on the order of
  records within a file except through silver row order.
- Idempotency: reruns never duplicate a key; changing one steps record changes exactly that
  day's step columns and no other gold cell; changing one survey row or sleep session does
  not change step columns.
- Full rebuild: steps silver and steps quality rows reflect only the current inputs.
- Raw immutability: raw files unchanged, nothing created under `data_dir`.
- `run_id` is unchanged.
- Scale: the real steps files hold about 2 million records. Row-by-row `executemany` was
  measured at about 0.77 ms per row on this machine (100,000 rows in 77 s), which would take
  over 25 minutes; a CSV `COPY` of 1,000,000 rows took 1.8 s. The implementation therefore
  bulk-loads `silver_steps_minute` (including `steps_per_minute` and `activity_level`) and
  the steps rows of `quality_rejects` (for example a temporary CSV loaded with `COPY`, removed
  afterwards and never created under `data_dir`). A test runs 60,000 records (12,000 of them
  converted hourly records) through the pipeline under 25 s. The real-data run time is
  recorded; no other target is set.
