# INC-009: Containerized End-to-End Run

Status: Approved (decisions D1-D9 in section 11 ratified by the human at G3 on 2026-10-14)
Source intent: `intents/INC-009-containerized-run.md` (kind: `environment`)
Unchanged: pipeline behavior and outputs, table schemas, `run_id`, the CLI surface, the specs and
tests of INC-002 to INC-008, `data/`, `README.md`, `notebooks/`.

## 1. Scope and artifacts

One image and one compose service. The implementation phase owns, and may only change:
`Dockerfile`, `.dockerignore`, `docker-compose.yml`, `pyproject.toml`, `uv.lock` (and `reports/INC-009/`).
No `src/` change is planned (D9). `tests/test_container.py` is fixed at planning.

## 2. Data contract (what crosses the container boundary)

| Path in container | Host path | Mode | Content |
|-------------------|-----------|------|---------|
| `/data` | `./data` | read-only (`:ro`) | raw input tree (same layout the CLI already reads) |
| `/output` | `./output` | read-write | the DuckDB database, quality report and run state the CLI already writes |
| `/app` | none | image | code, locked virtualenv, tests; never `data/` or generated output |

Outputs, grains, keys and schemas are exactly those of the existing CLI. All state lives in
`/output`; no named volume, no state in the image or in a container layer. A rerun or
`--mode incremental` after a container restart reads its previous state from `/output` only.

## 3. Image (`Dockerfile`)

- One image for both uses. `CMD` (exec form, JSON array), no `ENTRYPOINT` (D3):
  `["python", "-m", "wearable_pipeline", "run", "--data-dir", "/data", "--output-dir", "/output"]`.
  The harness runs `docker run --rm <image> python -m pytest -q`; an `ENTRYPOINT` would turn that into CLI arguments.
- Base image: `python:3.12.<patch>-slim-<debian-codename>` with an exact patch tag, never `latest` or a floating
  minor tag (D1). Any other image reference (for example `COPY --from=ghcr.io/astral-sh/uv:<x.y.z>`) is also
  pinned to an exact tag. An optional `@sha256:` digest is allowed.
- Dependencies: copy `pyproject.toml` and `uv.lock`, then `uv sync --frozen --extra dev` (or `--locked`), so the
  locked DuckDB is installed on every rebuild. `pip install '.[dev]'` is not used. `--extra dev` keeps `pytest -q`
  runnable inside the container. The project's own code is on the import path (`PYTHONPATH`, editable install or
  `uv sync` of the project); `python -m wearable_pipeline` works from any working directory.
- Non-root (D2): the final `USER` is a non-root account (default UID/GID 1000, build args `APP_UID`/`APP_GID`).
  `HOME` is set to a writable path, `PYTHONUNBUFFERED=1` is set. The virtualenv and code are world-readable so an
  arbitrary `--user` UID can run the image. `pytest -q` passes as the non-root user.
- No data and no outputs in the image: no `COPY`/`ADD` of `data` or `output`; `.dockerignore` section 5; no
  `VOLUME` pre-population.

## 4. Compose service (`docker-compose.yml`)

Service name `pipeline` (D4), the only service, `build: .`:

```yaml
services:
  pipeline:
    build: .
    user: "${HOST_UID:-1000}:${HOST_GID:-1000}"
    volumes:
      - ./data:/data:ro
      - ./output:/output
```

- Short volume syntax only, exactly those two entries; no top-level `volumes:`; no `command`/`entrypoint`
  override (the image `CMD` is the default); no `ports`, `restart`, `mem_limit`, `cpus`, `deploy` (no resource limit).
- One command: `docker compose run --rm pipeline` (D6 mentions the `up` alternative) runs the full pipeline.
- Arguments pass through by replacing the command (same image and service):
  - incremental: `docker compose run --rm pipeline python -m wearable_pipeline run --mode incremental --data-dir /data --output-dir /output`
  - compare: `docker compose run --rm pipeline python -m wearable_pipeline compare /output /other` (second output
    directory mounted with `-v`).
  - tests: `docker compose run --rm pipeline python -m pytest -q`.
  - plain Docker: `docker run --rm --user "$(id -u):$(id -g)" -v "$PWD/data:/data:ro" -v "$PWD/output:/output" <image>`.
- Host UID/GID: on a host whose user is not 1000, run with `HOST_UID=$(id -u) HOST_GID=$(id -g)` exported (D2).
  The documentation of these commands belongs to INC-010; INC-009 records them in the implementation report only.

## 5. `.dockerignore`

Excludes at least `data`, `output`, `.git`, `.venv`, `*.duckdb` (plus the existing caches). It must not exclude
`Dockerfile`, `docker-compose.yml`, `pyproject.toml`, `uv.lock`, `README.md`, `src`, `tests`, `scripts`, `specs`,
`intents`, `reports`, because the suite (including `tests/test_container.py` and `tests/test_orchestrator.py`) runs
inside the container.

## 6. Failure and safety behavior (existing CLI behavior; pinned, not changed)

Verified by reading `cli.py`, `pipeline.py`, `incremental.py` and by the passing tests in `tests/test_container.py`:

| Situation | Behavior | Exit |
|-----------|----------|------|
| `/data` not mounted/absent | `error: data directory not found: ...` (stderr), nothing written | 1 |
| `/data` present but empty or missing required inputs | `error: required input missing: ...`, nothing written | 1 |
| unreadable raw files | `error: cannot read raw files: ...` | 1 |
| `/output` exists but is unwritable (full and incremental) | `error: database write failed: ...`, no traceback, output unchanged | 1 |
| pipeline failure | `error: ...`, previous output unchanged (INC-006) | 1; compose propagates it |
| `compare` finds a difference | difference report | 1 |

Known limits, not fixed here (D9): an unwritable output is detected when the database is opened, after the raw files
are read and transformed (late, not instant); an output directory that does not exist under an unwritable parent
raises an unhandled `PermissionError` (still non-zero, with a traceback). Docker creates a missing `./data` bind
source as an empty root-owned directory, which then fails with `required input missing`. The read-only mount (`:ro`)
is what protects the raw data; the pipeline also succeeds on a read-only tree and leaves it byte-identical (tested).

## 7. Reproducibility and resources

Two container runs on the same data give identical tables, quality report and `run_id` (`compare` exit 0). The
implementation report records peak memory (about 4.9 GB expected) and timings. No resource limit is set.

## 8. Dependency declaration (the red-gate prerequisite, D5)

`pyyaml` is added to the `dev` optional dependency (`pyproject.toml`, `uv.lock` re-locked with `uv lock`; no
existing pin may change, notably DuckDB). It is needed because the contract tests parse `docker-compose.yml` and the
standard library has no YAML parser. It is a dev dependency only: `[project].dependencies` stays
`["duckdb>=1.4"]`. After adding it the implementer installs it (`uv sync --extra dev` or `pip install -e '.[dev]'`).

## 9. Verification gates

Planning (environment red gate): `python -m pytest -q` shows exactly `1 failed`, the failure is
`tests/test_container.py::test_environment_smoke` with `ModuleNotFoundError: No module named 'yaml'`; all other
tests pass or skip. Tests that need PyYAML or the not-yet-created `docker-compose.yml` skip at planning time and are
unskipped by the implementation (the smoke test fails, never skips, if either is still missing then).

Implementation:

1. `python -m pytest -q` passes locally: 0 failed, `test_environment_smoke` passes, no `test_container.py` static test skipped.
2. `WEARABLE_DOCKER_TESTS=1 python -m pytest tests/test_container.py -q` passes on a host with Docker (builds the
   image; synthetic fixtures only; covers default run, host-readable output, compare, incremental, `:ro`, fail-fast, no data in image, non-root).
3. Harness: image builds; `python -m pytest -q` passes inside the container.
4. Phase edits confined to the allowed paths in section 1 and `reports/INC-009/`.

## 10. Human real-data evidence checklist (recorded in the implementation report with commands and outcomes)

1. One-command compose full run succeeds and produces the output tables and report.
2. Read-only mount enforced: a write to the data mount fails; `data/` SHA-256 unchanged.
3. Second run reproduces identical tables, report and `run_id` (`compare`).
4. Incremental run with no change is a no-op; incremental vs full on a corrected data copy is identical.
5. Missing data mount and unwritable output directory each exit non-zero with a clear message.
6. Non-root container user writes the mounted output; host user can read it.
7. Timings and peak memory recorded.
8. Image contains no data or outputs (for example `docker run --rm <image> ls -A /data /output`, `docker history`, `docker save | tar -t` scan).

## 11. Planning decisions (gate G3: D1-D9 ratified by the human on 2026-10-14, unchanged)

- D1 Base image/pinning: `python:3.12.<patch>-slim-<codename>` exact tag (patch matching the lock's resolved 3.12; `.python-version` says 3.12.6), `uv` copied from a pinned `ghcr.io/astral-sh/uv:<x.y.z>`; digest optional. Tested by regex (no `latest`, no floating tag).
- D2 User/UID: image user UID/GID 1000; compose `user: "${HOST_UID:-1000}:${HOST_GID:-1000}"`; arbitrary UID must work (world-readable venv, writable `HOME`). Alternative: build-time UID only (rebuild per user).
- D3 Command form: `CMD` only, no `ENTRYPOINT`, so `docker run image python -m pytest -q` keeps working; arguments pass through by replacing the command (more verbose than an entrypoint).
- D4 Service `pipeline`; mounts `./data:/data:ro`, `./output:/output`; short syntax.
- D5 Red gate: declare `pyyaml` as a dev dependency (genuinely needed to test the compose file); `test_environment_smoke` imports it, so it fails with `No module named 'yaml'` until the implementation adds it. Other container tests skip while PyYAML/compose are absent. Rejected: a fake/unused dependency; importing a nonexistent `src` module; asserting on Docker availability (not a module error). Trade-off: contract tests are green-by-skip at planning and the Docker behavior tests are opt-in; the checklist in section 10 covers real data.
- D6 One command is `docker compose run --rm pipeline` (it attaches stdio and propagates the exit code); `up` is not used.
- D7 Opt-in Docker tests (`WEARABLE_DOCKER_TESTS=1`) are not run by the harness gate (no Docker inside the container, and the build is slow); they are an implementation gate run by the implementer on the host.
- D8 No resource limits, restart policy or ports (intent).
- D9 No `src/` change: fail-fast behavior already exists (section 6). Residual late detection of an unwritable output and the unhandled `PermissionError` for a missing output directory under an unwritable parent are accepted. Alternative: a small preflight in `cli.py`/`pipeline.py` (flagged `src/` change).
